# hifa — local issue tracker (v1)

> **Scope of this document:** it is the **v1 vertical spec**: scope, requirements and acceptance
> criteria for the whole MVP. **It does not define contracts.** The schema belongs to
> `specs/010-data-model.md`, the commands to `specs/050-cli.md`, the endpoints to
> `specs/060-api-rest.md`, the views to `specs/070-web-dashboard.md` and the error map to
> `SPEC-000 §6`. On any divergence the component wins and this document is corrected (D-005).
>
> `component: support` because the template enum (`domain | persistence | application |
> entry | support`) has no `vertical` value; `implements:` points to the acceptance
> artifacts that this spec does govern (there is no code of its own in the vertical).

## 1. Responsibility and boundaries

An issue tracker that runs entirely on the user's machine: a SQLite file as the single source of
truth, a CLI that needs no server and a lightweight web dashboard that starts only when it is
needed. It implements a complete issue-tracker model (states with a semantic type, identifiers
per team, fractional ranking, layered soft delete) so that daily work and agents can script against
something predictable, with no account, no network and no Node build step.

**Does NOT do (explicit):**

- It does not define the schema or the migrations (SPEC-010 §3, D-008: **a single DDL**).
- It does not define commands, flags or global flags (SPEC-050 §2.5); nor endpoints (SPEC-060 §2);
  nor dashboard routes or fragments (SPEC-070 §2). §2 enumerates them by reference, it does not
  rewrite them.
- It does not define exit codes or error codes: the map is `SPEC-000 §6` and `SPEC-050 §6` (D-014).
- It does not define the search contract (SPEC-090 §2, D-002/D-016) or the import/export one
  (SPEC-080).
- It does not cover post-v1: multi-user, sync, AI, binary attachments, notifications (see §10).

## 2. Public contract

v1 does not invent a contract: it composes it from the owners. Reference table (all normative):

| Surface | Owner | What v1 takes from it |
|---|---|---|
| Schema, migrations, views, FTS | SPEC-010 §3 | 17 tables + `issue_fts`, 3 views, migrations 001/002/003 |
| Commands, flags, `--json`, `--quiet` | SPEC-050 §2.5 | full surface of §4 of this document |
| HTTP endpoints (`/api/v1/*`, `/healthz`) | SPEC-060 §2 | REST API of REQ-F034 |
| Dashboard routes and fragments | SPEC-070 §2 | `GET /`, `/{team}/board`, `/{team}/list`, `/{team}/issue/{identifier}`, `/_/*` |
| Domain errors → exit/HTTP | SPEC-000 §6 | single table (A7) |
| Search | SPEC-090 §2 | `--limit` 1-200 default 50; over `{hits,total,has_more,backend,took_ms}` |
| Import/export | SPEC-080 §2 | CSV/JSON formats and `JOURNAL_ORDER` |
| `init` / `doctor` / config | SPEC-100 §2 | canonical seeding and `doctor` exit codes (0/1/2/3) |

Two contracts that the vertical **does** fix, because they cut across all of its REQs (and that
the edges already implement the same way):

- **`--json` output:** a single JSON document per invocation. A single entity is emitted as the
  canonical object of SPEC-050 §2.4.2 (no wrapper); a list, with the envelope
  `{items, next_cursor, has_more, total_estimate}`; `hifa search`, with the envelope of SPEC-090 §2.
  Errors go to **`stderr`** as `{"error":{"code","message","field"}}` and `stdout` stays empty.
  Zero ANSI, zero human text on `stdout`.
- **Exit codes:** `0` ok · `2` validation · `3` not found · `4` conflict · `5` invalid transition
  · `6` internal/corrupt database · `130` interrupted (D-014). `hifa doctor` uses `0/1/2/3`
  (SPEC-100 §6, D-001) and is the only exception.

## 3. Data it touches

The MVP uses the full schema of SPEC-010 §3. **There is no DDL in this document** (D-008): the
single source is `specs/010-data-model.md`. Map from model entity → table, to orient the
reading of the requirements:

| Model entity | SQLite table | Notes |
|---|---|---|
| Organization (workspace) | `workspace` | 1 row in v1 (`url_key` unique) |
| Team | `team` | `UNIQUE(workspace_id, key)`; **no counter**: `number` comes from `MAX(number)+1` (R2 of 010) |
| WorkflowState | `workflow_state` | `type` with 6 values; `position` REAL; `UNIQUE(team_id, id)` |
| IssueLabel | `label` | `team_id NULL` = workspace; groups via `parent_id`; uniqueness through partial indexes (D-010) |
| User | `member` | local users, no auth |
| TeamMembership | `team_membership` | composite PK (team, member) |
| Issue | `issue` | `identifier` UNIQUE; `workspace_id` + composite FK `(team_id, state_id)` |
| Issue↔Label | `issue_label` | M2M with composite PK |
| IssueRelation | `issue_relation` | `blocked_by` is derived, it is not stored |
| Comment | `comment` | `parent_id` for threads, `resolved_at` |
| Attachment | `attachment` | link + `metadata` JSON, no files |
| Project | `project` | `status_type` + `priority` 0-4; `workspace_id` |
| ProjectMilestone | `project_milestone` | `status` with 4 values |
| Cycle | `cycle` | `number` per team, ISO range |
| IssueHistory | `issue_history` | per-field audit |
| Historical key of a team | `team_previous_key` | migration 003; resolves old identifiers (R3) |
| Search | `issue_fts` (virtual FTS5) | external content over `issue`, `identifier UNINDEXED` |
| Schema ledger | `schema_migration` | migration 002; versions 1..3 |

Invariants that v1 **requires** and that the schema already guarantees: `UNIQUE(team_id, number)`,
`UNIQUE(identifier)`, composite FK `(team_id, state_id)` (R4), label uniqueness per scope
(D-010), `due_date` with a real calendar (D-009) and layered soft delete (D-015: there is no
physical delete).

## 4. Business rules

Conventions: `REQ-F*` functional, `REQ-N*` non-functional, `REQ-S*` security. All entity IDs are
ULIDs in `TEXT`; all timestamps are ISO-8601 UTC
(`YYYY-MM-DDTHH:MM:SS.sssZ`); all calendar dates (`due_date`, `start_date`,
`target_date`) are `TimelessDate` in `TEXT` with format `YYYY-MM-DD`.

### 4.1 Functional — data core

- **REQ-F001** — `hifa init` creates the `.db` file, applies the migrations up to
  `user_version = 3` (17 tables + `issue_fts` with its 3 triggers, 3 views) and seeds in **a single
  transaction**: 1 workspace, 1 team, **6 workflow states** (`Triage`/triage at 1.0, `Todo`/unstarted
  with `is_default=1` at 2.0, `Backlog`/backlog at 3.0, `In Progress`/started at 4.0,
  `Done`/completed at 5.0, `Canceled`/canceled at 6.0 — `Todo` **before** `Backlog`, D-034),
  **4 labels** (`Bug`, `Feature`, `Improvement`, `Docs`) and 1 local member with
  its membership (D-013). If any step fails, no partial `.db` file is left on disk.

- **REQ-F002** — `hifa init` is idempotent: a second run over an already initialized database
  ends with exit code `0`, reports `already initialized` and does not duplicate any row (counts of
  `team`, `workflow_state`, `label`, `member` identical before and after).

- **REQ-F003** — `hifa init` refuses to operate on an existing file that is not a hifa database
  (no `workspace` table), unless `--force`. In that case it exits with exit code `2`, does not modify
  the file and the message names the exact path.

- **REQ-F004** — The database path is resolved with the precedence of SPEC-050 §2.2.1 (`--db` >
  `HIFA_DB` > `workspace.db` from `.hifa.toml` > XDG), and `hifa info` prints the effective path and
  the origin (`flag`, `env`, `config`, `xdg`). Relative paths are resolved against the cwd and
  printed as absolute.

- **REQ-F005** — `hifa team create ENG Engineering` validates the key against
  `^[A-Z][A-Z0-9]{1,9}$` (2-10 characters, A-Z and digits, starting with a letter; SPEC-020 §2.2 is
  the owner of `KEY_PATTERN`): the key is normalized first (`strip()` + `upper()`, so `eng` becomes
  `ENG`), stored in uppercase, and duplicates are rejected within the workspace (exit code `4`,
  writing nothing). `icon` accepts any UTF-8 string (emoji) of 1 to 8 code points; `timezone`
  defaults to `America/Santiago`.

- **REQ-F006** — `hifa team set-key OLD NEW` rewrites in a transaction the `identifier` of every
  issue of the team (`NEW-<number>`, same `number`), writes a row in `issue_history` with
  `field='identifier'` for each affected issue and records the previous key in
  `team_previous_key(team_id, key, changed_at)` (migration 003). An old identifier still
  resolves in `hifa issue show` with a warning on `stderr`.

- **REQ-F007** — *(deferred, D-031)* `hifa team archive ENG` sets `archived_at`; the team disappears
  from `hifa team list` (unless `--all`), from `hifa board` without `--team` and from the command
  palette, but its issues remain queryable by identifier. **This requirement is not part of the v1
  CLI surface**: `archive_team` is deferred with `update_team` (D-031), SPEC-050 publishes no `team
  archive` row, and the open-issues guard (`Validation` ⇒ exit 2 in SPEC-040 vs `Conflict` ⇒ exit 4
  in the old edge text vs idempotent ⇒ exit 0 in SPEC-050 R5) is settled by the revision that
  implements it. The previous `--force` flag is gone with the command; no edge invents a flag the
  use case cannot carry (D-012).

- **REQ-F008** — `hifa state add --team ENG --name "In Review" --type started` accepts any free
  name and requires `--type` within `triage|backlog|unstarted|started|completed|canceled`; the
  name is unique per team (case-insensitive, exit code `4` on duplicate) and `position` is assigned
  as the team's `max(position)+1.0` when `--position` is not passed.

- **REQ-F009** — `hifa state delete <state>` is rejected with exit code `4` if there are issues
  pointing to that state, unless `--move-to <state>` is passed; with `--move-to`, the reassignment of
  issues, the `issue_history` rows (`field='state_id'`) and the deletion of the state happen in a
  single transaction (or all are rolled back).

- **REQ-F010** — Timestamps are derived from the `type` of the target state, never from the name:
  entering a `started` state sets `started_at` if it was `NULL`; entering `completed` sets
  `completed_at`; entering `canceled` sets `canceled_at`; leaving `completed`/`canceled` towards an
  open type clears the corresponding timestamp to `NULL`. Previous timestamps are never overwritten
  if they already existed.

- **REQ-F011** — `hifa issue add --team ENG --title "..."` assigns `number` with the team's
  `MAX(number)+1` inside `BEGIN IMMEDIATE` (SPEC-030 §2.5 SQL-1, R2 of SPEC-010) and
  `identifier = team.key || '-' || number`. There is no per-team counter: the writer lock plus
  `UNIQUE(team_id, number)` guarantee uniqueness, with up to **3** retries of the use case on
  collision (D-018). Numbers are per team, start at 1 and are never reused: with no physical
  delete (D-015), `MAX(number)+1` is monotonic.

- **REQ-F012** — `hifa issue show` accepts three reference forms: `identifier` (`ENG-12`), full
  ULID (26 chars) and integer number with `--team ENG`. It also resolves historical identifiers
  (old key in `team_previous_key` + `number`) and prints an `identifier renamed` warning on `stderr`.
  A non-existent reference exits with exit code `3` and `error.code="not_found"`.

- **REQ-F013** — `hifa issue update` accepts a subset of
  `title, description, priority, estimate, state, assignee, due_date, project, milestone, cycle,
  parent, labels, sort_order, board_order`. Unknown fields abort with exit code `2` and a list
  of valid fields; the update is a single transaction and writes exactly one row of
  `issue_history` per field whose value changed (no rows for identical values). `updated_at` is
  bumped only once.

- **REQ-F014** — `hifa issue close|cancel|reopen` operate by `type`, not by name: `close` moves to
  the team's first `completed` state by `position`, `cancel` to the first `canceled`, `reopen` to
  the `unstarted` state with `is_default=1` (or the first `unstarted` by `position` if there is no
  default) and clears `completed_at`/`canceled_at`. The three commands are idempotent: applying them
  twice does not change the result nor duplicate history.

- **REQ-F015** — Deletion is layered and **all** layers are reversible (D-015: there is no physical
  delete): `hifa issue trash` sets `trashed=1` (it leaves listings, board and search, it stays
  visible with `hifa issue list --trashed`), `hifa issue untrash` reverts it and `hifa issue archive`
  sets `archived_at` without touching the state. The cleanup of `issue_fts` is done by the
  `AFTER DELETE` triggers of `issue` (external content), not by a FK cascade. There is no physical
  delete (D-015): a hard-delete flag is an unknown flag and aborts with exit code `2`
  (`invalid_option`).

- **REQ-F016** — `hifa issue list` combines filters with AND across families: `--team`, `--state`
  (repeatable, OR inside the family), `--state-type` (repeatable, OR), `--priority` (repeatable, OR,
  `0`-`4`), `--assignee` (member name, email or id), `--mine`, `--unassigned`, `--label` (repeatable,
  **all** must be present), `--project`, `--cycle`, `--no-cycle`, `--parent` (direct children only),
  `--query` (title filter, D-025), `--open`/`--all`, `--archived`, `--trashed`, `--sort`, `--reverse`,
  `--limit` (**default 50, range 1-200**, D-011) and `--cursor`. The visibility axes are the ones of
  SPEC-050 §2.5.3.1: `--archived` and `--trashed` select one layer each, the trash is the deeper one, so
  `--trashed` returns the archived-then-trashed issues too. `--json` returns the same set as the table,
  with the same order and the same `limit`, in the envelope
  `{items, next_cursor, has_more, total_estimate}`.

- **REQ-F017** — The order is total, deterministic and documented. `--sort` accepts
  `manual|priority|created|updated|due` (default `manual` = `sort_order`, D-011), ascending, with `id`
  ascending as the final tie-breaker; `--reverse` inverts the key and the tie-breaker together. Rows
  without a value are **last in both directions** (D-044): the key expresses absence as `NULL`, never as
  a sentinel, so `No priority` and the undated issues close the listing under `--reverse` as well. The
  cursor is `base64url("<order>:<asc|desc>|<ULID>")`, the direction in lowercase and the token opaque to
  the client (SPEC-030 §2.6.2); it names the ordering it was built for, so a cursor from another
  `--sort` or from the other direction is exit 2 `validation_error` with `field: "cursor"`. Two runs
  over the same data produce the same order byte by byte.

- **REQ-F018** — `hifa board --team ENG` groups by `workflow_state` ordered by `position ASC` and,
  inside each column, orders by `board_order ASC` with `number ASC` as tie-breaker. Each column
  reports `count` and `wip` (`count` of issues with `state_type='started'`). `--json` returns
  `{"columns":[{"state":{...},"issues":[...]}]}`; columns of type `triage` with
  `triage_enabled=0` are not shown.

- **REQ-F019** — `hifa issue move ENG-12 --to-state "In Progress" [--before X] [--after Y]` computes
  the new `board_order` by fractional ranking: between two neighbours `(a+b)/2`, at the end
  `last+1024.0`, at the beginning `first-1024.0`. If the resulting gap is smaller than `1e-4`, the
  whole column is renumbered with step `1024.0` inside the same transaction and the command reports
  `rebalanced: true` in `--json`.

- **REQ-F020** — Sub-issues use `parent_id` (self-reference) and `sub_issue_sort_order`;
  `hifa issue sub ENG-12 --title "..."` creates the child with
  `sub_issue_sort_order = max+1024.0` among its siblings. The maximum depth is **5** (root =
  level 1); attempting level 6 fails with exit code `4`, `error.code="conflict"`,
  `field="parent"` and the limit in the message. `hifa issue tree ENG-12` prints the full tree with
  2-space indentation per level.

- **REQ-F021** — `hifa issue relate ENG-1 blocks ENG-2` accepts
  `blocks|duplicate|related|similar` and persists **one** row in `issue_relation` (directional for
  `blocks`). `blocked_by` is not stored: `hifa issue blocking ENG-2` derives it by querying
  `type='blocks'` in the reverse direction. Self-relation (`issue_id = related_issue_id`) and exact
  duplicates are rejected with exit code `4`.

- **REQ-F022** — `hifa issue comment ENG-12 --body "text"` creates a markdown comment; `--body -`
  reads the body from stdin and `--parent <comment-id>` creates a nested comment (maximum depth 3).
  `hifa comment resolve <id>` sets `resolved_at` and `hifa comment list` hides the resolved ones unless
  `--resolved`. `hifa comment edit <id> --body` sets `edited_at` and leaves the original `created_at`
  untouched.

- **REQ-F023** — `hifa issue attach ENG-12 --url file:///home/x/captura.png --title "Screenshot"
  [--metadata '{"w":1920}']` stores the link and the metadata JSON without uploading or copying files;
  an invalid `--metadata` (unparseable JSON or not an object) fails with exit code `2`. Only the
  schemes `file`, `http` and `https` are accepted.

- **REQ-F024** — `hifa label add --name Bug --color "#EB5757"` creates a workspace label when
  `--team` is not passed, or a team label when it is. Both levels can coexist with the same name
  (partial unique indexes, D-010). Groups (`--group --group-type multiSelect|singleSelect`)
  contain child labels via `parent_id`; in a `singleSelect` group, assigning a second label of the
  same group **replaces** the previous one and returns `replaced: <label>` in `--json`.

- **REQ-F025** — `hifa search "login bug"` uses the contract of SPEC-090 §2: `--limit` default **50**
  with range **1-200**, normalized `bm25` ranking (higher score = better), exclusion of `trashed=1` and
  `archived_at IS NOT NULL` at query time, `snippet` with `<mark>` markers and the envelope
  `{hits, total, has_more, backend, took_ms}` with `backend` ∈ `fts|like|none`. The index rebuild
  is `hifa db reindex` (D-003); `hifa search --reindex` does not exist.

- **REQ-F026** — `hifa cycle add --team ENG --starts 2026-11-02 --ends 2026-11-15` assigns a
  sequential `number` per team (`max+1`) and validates `ends_at > starts_at` (exit code `4`);
  `--starts`/`--ends` accept `YYYY-MM-DD` (interpreted as 00:00 in `team.timezone` and stored as
  ISO-8601 UTC) or a full ISO datetime. A cycle that overlaps another one of the same team is
  rejected unless `--allow-overlap`; with `--allow-overlap` it is written anyway and `hifa doctor`
  reports the overlap. `hifa cycle current --team ENG` returns the cycle whose range contains the
  current instant in `team.timezone`.

- **REQ-F027** — `hifa project add` and `hifa milestone add` create projects (`status_type`,
  `priority` 0-4, `lead_id`, `start_date`, `target_date`) and milestones (`status` within
  `unstarted|next|overdue|done`). `hifa project show` computes `progress` as
  `issues with state_type in ('completed') / total issues of the project`, as an integer percentage
  rounded down, and `0` when there are no issues.

- **REQ-F028** — Every issue mutation writes `issue_history` with `actor_id`, `field`,
  `old_value`, `new_value` and `created_at`. `hifa issue history ENG-12` prints the rows in
  ascending chronological order with the actor resolved to `display_name`, and `--json` returns
  `old_value`/`new_value` as JSON strings (not as free text) so that an agent can
  parse them.

- **REQ-F029** — `hifa export --format csv` emits exactly these columns, in this order:
  `Identifier, Title, Description, Assignee, Priority, Status, Labels, Project, Cycle, Estimate,
  Due Date`. `Priority` uses the label derived from `v_priority` (`Urgent`, `High`, `Medium`, `Low`,
  `No priority`), `Status` the `workflow_state.name`, `Labels` separated by comma inside a quoted
  field, dates as `YYYY-MM-DD`. CSV RFC 4180, UTF-8 without BOM, `\n` as line ending. `-o -`
  writes to stdout.

- **REQ-F030** — `hifa import file.csv --team ENG` maps the same columns to entities:
  `Priority` label→0-4, `Status` name→`workflow_state.id` of the team, `Labels` create-or-link,
  `Due Date` strict ISO. `--dry-run` validates the whole file and reports
  `{"would_create":N,"would_update":M,"errors":[...]}` without writing. An invalid state or date
  aborts **before** inserting and the error names the line number. `--on-conflict
  skip|update|fail` (default `fail`, SPEC-050 §2.5.5) decides what to do when the `Identifier`
  already exists.

- **REQ-F031** — `hifa export --format json` produces a document
  `{"schema_version":3,"exported_at":"...","workspace":{...},"teams":[...],"issues":[...],...}` with
  all the original ULIDs, and `hifa import --format json` over an empty database restores the same
  entities with the same IDs, `number` and `identifier` (byte-by-byte round-trip of the issues JSON
  except `updated_at`). `schema_version` of the dump = `user_version` of the database (`3` in v1).

- **REQ-F032** — All commands accept the global `--json` and emit exactly one JSON document
  on `stdout`, with the shape of §2: canonical object for one entity, list envelope for lists, and
  `{"error":{"code","message","field"}}` on **`stderr`** with a non-zero exit code. With `--json`
  no ANSI, no spinners and no human text are emitted on `stdout` (warnings go to `stderr`). Error
  codes: those of SPEC-050 §6 (`validation_error`, `not_found`, `conflict`, `invalid_transition`,
  `internal_error`, …); exit codes those of §2 (D-014).

- **REQ-F033** — `hifa serve` starts a single uvicorn process (no gunicorn, no multiple workers)
  with default host `127.0.0.1` and **default port `7777`** (the one in SPEC-040 §2, authority for the
  application port per D-012, confirmed in SPEC-060 §2 and SPEC-100 §2.3), prints the effective URL
  and serves the dashboard; `--open` opens the browser. The FastAPI app is
  built on the same services as the CLI (zero business logic in routes) and exposes
  `/openapi.json` generated from the Pydantic models.

- **REQ-F034** — The REST API is the one in SPEC-060 §2: prefix `/api/v1`, `GET /issues` (the same
  filters as `hifa issue list`, `limit` ≤ 200 and keyset cursor), `GET /issues/{ref}`,
  `POST /issues`, `PATCH /issues/{ref}`, `GET /teams`, `/states`, `/labels`, `/cycles`,
  `GET /export?format=csv|json`, `GET /search` and `GET /healthz` (no prefix). A non-existent
  identifier returns `404` with `{"error":{"code":"not_found",...,"field":"ref"}}`; an invalid body
  returns `422` with the Pydantic detail. The dashboard consumes these routes, not a
  variant of its own.

- **REQ-F035** — The dashboard renders server-side (Jinja2) the views of SPEC-070 §2: board by
  state (`GET /{team}/board`), list with filters (`GET /{team}/list`) and issue detail
  (`GET /{team}/issue/{identifier}`), plus the htmx fragments of `/_/*` (rows, board column,
  comments) that are updated without a reload. `GET /` redirects (`303`) to the default team's
  board. Alpine.js is used only for local UI state (palette open/closed, collapsed filters);
  there is no business state on the client.

- **REQ-F036** — The command palette (`GET /_/palette?q=log`, owner SPEC-070 §2) returns at most
  10 mixed results ordered by relevance with `kind` in `issue|team|label|command`, each
  one with `title`, `subtitle` and `href` (or `command` for actions), in under 100 ms with
  10 000 issues.

- **REQ-F037** — `hifa doctor` reports `schema_version`, results of `PRAGMA quick_check`,
  `PRAGMA foreign_key_check`, counts per table, file size, FTS desynchronization
  (comparing `count(issue)` with `count(issue_fts)`) and overlapping cycles. The exit codes are
  those of SPEC-100 §6 (D-001): `0` ok, `1` warn, `2` fail, `3` not diagnosable. `--fix-fts` and
  `--vacuum` are the only maintenance actions; without flags it is read-only and exits with `1`/`2`
  if there are findings.

### 4.2 Non-functional

Reference measurements: host with 3.2 GB of RAM and ~770 MB free; test database with 10 000 issues
/ 200 000 comments / 50 labels / 3 teams; `python3.11` + `sqlite3` from the stdlib.

- **REQ-N001** — CLI latency measured as p95 over 100 runs on the reference database: read
  command (`hifa issue list --limit 50`, `hifa issue show`) ≤ 120 ms; write command
  (`hifa issue add`) ≤ 200 ms; cold start of the interpreter (measured with
  `hifa --version`) ≤ 250 ms. No single command exceeds 2 s.

- **REQ-N002** — Server memory: `hifa serve` at rest (RSS, measured with `/proc/<pid>/status`
  after 60 s without traffic) ≤ 120 MB; under 5 sustained concurrent requests ≤ 200 MB. The CLI never
  exceeds 80 MB of RSS in any command; CSV import/export is processed by streaming and does not load
  the whole file into memory. These budgets are **stricter** than those of
  SPEC-000 §4.4 (120 MB CLI / 150 MB serve): for v1 this document prevails.

- **REQ-N003** — Offline by design: zero network requests at runtime (no CDN, no fonts, no
  telemetry, no version check). The dashboard serves all assets from the installed
  package (`src/hifa/web/static/vendor/`); htmx 16 KB gzip and Alpine.js 16 KB gzip vendored;
  total JS on first load ≤ 40 KB gzip and CSS ≤ 15 KB gzip. A test verifies that no
  external `http://` or `https://` exists in the templates.

- **REQ-N004** — Portability: Python ≥ 3.11 on Linux and macOS, with no own compiled extensions
  and no external binaries (only `sqlite3` from the stdlib, with FTS5 verified at startup: if
  `PRAGMA compile_options` does not include `ENABLE_FTS5`, a clear error and exit code `6` with
  `error.code="fts5_unavailable"`). Windows is out of v1. The database is a single portable file
  (`hifa.db` + `-wal`/`-shm`), with no dependency on the absolute path.

- **REQ-N005** — Scale: with 10 000 issues, `hifa issue list` filtered ≤ 50 ms and unfiltered
  ≤ 150 ms; `hifa board --team` (10 columns, 2 000 issues) ≤ 150 ms; `hifa search` ≤ 100 ms. With
  50 000 issues and 200 000 comments the listing queries stay under 300 ms (the indexes of
  `issue` cover team+state, assignee, due_date, project, cycle and parent).

- **REQ-N006** — Concurrency: `journal_mode=WAL`, `busy_timeout=5000`, `foreign_keys=ON` and
  `synchronous=NORMAL` on **every** connection. Writers use `BEGIN IMMEDIATE` and retry
  up to **3** times with a 50 ms backoff on `SQLITE_BUSY` (D-018: the retry lives in
  `app/retry.py`, outside the `@contextmanager` of the UoW). Acceptance test: 20 processes
  `hifa issue add` in parallel on the same team produce 20 issues with numbers `1..20` without
  gaps or duplicate identifiers.

- **REQ-N007** — Size: with 10 000 issues and 200 000 comments the `.db` file ≤ 120 MB, and the
  FTS5 index ≤ 25 % of that size. `hifa doctor` reports both numbers and fails the test assertion
  if they are exceeded.

- **REQ-N008** — Output determinism: `--json` serializes with the field order of the Pydantic
  schema (not alphabetical), timestamps always UTC with `Z`, floats with stable `repr`, and arrays
  ordered by the same key as the table. The same command over the same database produces the same
  stdout.

- **REQ-N009** — Startup without side effects: no command other than `init`, `db migrate` or `import`
  creates or modifies the schema; opening a database with a lower `user_version` prints a warning and
  requires `hifa db migrate` (it does not migrate implicitly) so that an agent does not mutate data
  by accident.

- **REQ-N010** — The CLI works without a server and without a network, with direct access to SQLite;
  the dashboard is optional. `hifa init && hifa issue add` must work in a container with no open
  ports.

- **REQ-N011** — Migrations are forward-only and numbered with three digits (`001_init.sql`,
  `002_schema_migration.sql`, `003_team_previous_key.sql`), each applied in its own
  transaction and recorded in `schema_migration(version, name, applied_at, checksum)`. `hifa db
  migrate` is idempotent, detects a tampered checksum of an already applied migration and aborts with
  exit code `6` and `error.code="migration_checksum_mismatch"` without touching data (SPEC-010 §6).
  Before applying, a backup `hifa.db.bak-<version>` is written with `VACUUM INTO`.

### 4.3 Security

- **REQ-S001** — Path traversal: every path served by the dashboard is resolved with
  `Path(...).resolve()` and validated with `is_relative_to(static_root)`; a request with `..`,
  `%2e%2e` or a symlink escaping the root returns `404` (not `403`, to avoid revealing existence) and is
  logged without the raw path. Attachments with the `file://` scheme are only accepted if the
  resolved path is under `$HOME`; outside of it they are rejected with exit code `4` unless
  `--allow-any-path`.

- **REQ-S002** — SQL injection: 100 % of the queries use parameters (`?`/`:name`); interpolating
  with f-strings, `%` or `.format()` in SQL is forbidden (static test that fails if
  `execute(f"`/`execute("...%s" %` appears). The input of `hifa search` is tokenized and each term is quoted
  as an FTS5 phrase (internal quotes doubled), so that `"*" OR 1=1`, `NEAR(`, `col:x` and `-`
  are treated as literal text and never as operators; a search with hostile syntax returns 0
  results, not a `500` error nor extra rows.

- **REQ-S003** — Local bind by default: `hifa serve` listens on `127.0.0.1:7777`. Any
  `--host` other than loopback must be passed **explicitly**, prints a warning that there is no
  authentication in v1, does not enable CORS (no `Access-Control-Allow-Origin`, same-origin only) and
  ends with exit code `0` if the socket opens (SPEC-000 REQ-S001: there is no additional
  confirmation flag).

- **REQ-S004** — HTML sanitization: the markdown of descriptions and comments is rendered
  server-side with `markdown-it-py` (`html=False`) and passed through an own allowlist of
  tags/attrs/schemes (D-022; SPEC-070 §2.3.6) that removes `<script>`, `<style>`, `<iframe>`,
  `<object>`, `<form>`, all `on*` attributes, `style` and `javascript:`/`data:` URLs. The
  allowlist is implemented at the edge, with no dependency on an external sanitizer (D-022). In the
  list, board and palette views the text is escaped without rendering
  markdown. Mandatory test: `<script>alert(1)</script>` and `<img src=x onerror=alert(1)>` do not
  produce a script or a handler in the output HTML.

- **REQ-S005** — Dashboard writes: the htmx `POST`/`PATCH`/`DELETE` require the header
  `HX-Request: true`; without it the fragment responds `400` (SPEC-070 R5). There is no CSRF token,
  no `SameSite=Strict` cookie and no `Authorization: Bearer`; `serve` does not implement auth in v1
  (SPEC-000 REQ-S005) and the only client is the local browser.

- **REQ-S006** — Files and permissions: the `.db` file is created with mode `0600` and its directory
  with `0700`; if it already exists with broader permissions, `hifa doctor` reports it as a finding.
  Nothing is written outside the database directory except the explicit paths of `-o`/`--db`. No
  telemetry, no keys, no `.env` read implicitly.

- **REQ-S007** — Input limits: HTTP body ≤ 1 MB (`413` if exceeded), query string ≤ 2 KB,
  `limit` ≤ 200 in the CLI and in the API (D-011), import file ≤ 100 MB (read by streaming, aborts
  with exit code `2` and `field="file"` before loading), and JSON nesting depth ≤ 32.

- **REQ-S008** — Templates: Jinja2 with global `autoescape=True` and with no `|safe` outside the HTML
  already sanitized by the markdown layer; `StrictUndefined` enabled so that a missing variable fails
  in development instead of rendering empty. Test: a title with `<b>` is shown escaped in the
  list.

- **REQ-S009** — Supply chain: exact versions and hashes in `uv.lock`, no post-install
  scripts, and the vendored JS assets with their SHA-256 recorded in
  `src/hifa/web/static/vendor/CHECKSUMS`; a test compares the hashes in CI.

### 4.4 Edge cases

| ID | Case | Mitigation |
|---|---|---|
| EC-001 | **Two issues created at the same time in the same team** (two processes, or CLI + `serve`): both compute the same `MAX(number)+1` and would generate `ENG-7` twice | The `SELECT MAX(number)+1` runs inside `BEGIN IMMEDIATE` (SPEC-030 SQL-1): the second transaction waits for the lock and reads the number already inserted. `UNIQUE(team_id, number)` is the safety net; on violation the use case retries up to **3** times (D-018), and on `SQLITE_BUSY` `app/retry.py` retries with a 50 ms backoff. Verification: 20 parallel processes require `{1..20}` with no gaps. |
| EC-002 | **`delete workflow_state` with issues pointing to it** | The composite FK of `issue` is `RESTRICT` (not cascade), so the direct delete fails with `FOREIGN KEY constraint failed`. `hifa state delete` requires `--move-to <state>` and performs reassignment + `issue_history` (`field='state_id'`) + deletion in **one** transaction; without `--move-to` it exits with exit code `4` and prints how many issues block it. |
| EC-003 | **`due_date` in a different timezone** (user in `America/Santiago`, team in `Europe/Berlin`) | `due_date` is a `TimelessDate`: the string `YYYY-MM-DD` is stored and returned as is, with no conversion to UTC and no time attached. Validation rejects `2026-03-01T00:00:00Z` and impossible dates (`2026-13-45`, `2026-02-30`): CHECK of the schema (D-009) + `domain.rules`. The relative calculation ("due in 3 days", "overdue") is done by comparing against `date('now', team.timezone)` only at render time. |
| EC-004 | **Workspace label and team label with the same name** (`Bug` at both levels) | They are distinct, valid rows (separate partial unique indexes, D-010). When resolving `--label Bug` without `--team`, the rule is: label of the context's team > workspace label; if there is more than one candidate (e.g. two teams with `Bug` and none in context), the command emits a warning on `stderr` with the IDs instead of picking one at random. In `--json`, every label is always identified by `id` (ULID), never by name. |
| EC-005 | **Cycle overlapping another one of the same team** | The DDL cannot express "do not overlap ranges" without a trigger; validation lives in `cycle_service`: it compares `[starts_at, ends_at)` against the team's existing cycles and rejects with exit code `4` showing the conflicting cycle (number and range). `--allow-overlap` writes anyway and adds a permanent finding that `hifa doctor` reports. `hifa cycle current` with an overlap returns the one with the highest `number` and warns on `stderr`. |
| EC-006 | **Sub-issue 3 levels deep** (root → child → grandchild → great-grandchild) | Allowed up to depth 5. `hifa issue tree` renders with 2-space indentation per level and does not truncate. At level 6, `issue add --parent`/`issue sub` fails with exit code `4` **before** inserting. `hifa issue trash` of a parent propagates the trash to all descendants in the same transaction (so that no orphans are left visible on the board); a child is only removed from the view with `trash`, it is not deleted (D-015). |
| EC-007 | **Trashed issue that shows up in search** | The FTS index does not store the flag: the triggers always index and the search query does `JOIN v_issue ... WHERE trashed=0 AND archived_at IS NULL` (the view exposes `visible`, D-019). `untrash` brings it back to the results without reindexing. Verification: trash → `hifa search` does not find it → untrash → it appears with the same `snippet`. |
| EC-008 | **Read-only database** (file `0444`, read-only filesystem or full disk) | On open, a write probe is attempted (`BEGIN IMMEDIATE; ROLLBACK`) only if the command is going to write; if it fails, read commands keep working opening with `mode=ro`, and write commands exit with exit code `6` and `error.code="internal_error"` (D-014: it is an unusable environment) with a hint containing the path and the suggested `chmod`. Permissions are never "fixed" automatically. |
| EC-009 | **Corrupt `.db` file** (`SQLITE_NOTADB` / `SQLITE_CORRUPT`) | `hifa init` detects a file without a SQLite header and refuses (exit code `2`) without touching it. In any command, a corruption error is translated to `corrupt_database` with exit code `6` and the hint `hifa doctor`. `hifa doctor` runs `PRAGMA quick_check`; if it fails, it reports the state and suggests `VACUUM INTO` to a new file (reporting unreadable rows). The original file is never deleted nor overwritten. |
| EC-010 | **Renamed team changes the identifier** (`ENG` → `PLAT`) | `team set-key` recomputes the `identifier` of every issue of the team (`PLAT-12`) keeping `number`, writes history (`field='identifier'`) and adds `ENG` to `team_previous_key`. `hifa issue show ENG-12` resolves through `team_previous_key` + `number` and warns `identifier renamed to PLAT-12` on `stderr`. An old key is never reassigned to another team because `number` is per team and is not recycled. `hifa search ENG-12` does not depend on the indexed identifier (it goes `UNINDEXED`): the match by identifier is resolved by `parse_query` of SPEC-090. |
| EC-011 | **Desynchronized FTS index** (someone wrote with `sqlite3` by hand or the process died in the middle of a trigger) | `hifa doctor` compares `count(issue)` against `count(issue_fts)` and reports the delta as a finding (`warn` ⇒ exit 1); `hifa db reindex` runs `INSERT INTO issue_fts(issue_fts) VALUES('rebuild')` and is the only corrective action (D-003). Idempotent, it does not touch the `issue` table. |
| EC-012 | **`serve` and CLI writing at the same time** | WAL allows concurrent readers with one writer. `serve` opens one connection per request (no long transactions) and closes it when the handler finishes; the CLI writer retries on `SQLITE_BUSY`. The dashboard never issues a long read `BEGIN` during a render: it queries, closes and renders with the already materialized models. |
| EC-013 | **Priority and manual order tie** | The order always includes tie-breakers: normalized priority (`0` last), `sort_order`, `number`. Two issues with the same `priority` and the same `sort_order` (CSV import) are ordered by `number`, so the listing is stable and `--json` is reproducible byte by byte. |
| EC-014 | **CSV with BOM, CRLF and accents** (exported from a spreadsheet on Windows/Excel) | The import reads with `utf-8-sig` (consumes the BOM), accepts `\r\n` and `\n` via `csv.reader` with the excel dialect, and normalizes to NFC to compare label/state names. A date that is not strict ISO is not guessed: it is rejected with the line number and the import aborts before inserting. Fields with commas or quotes are handled by RFC 4180 quoting. |
| EC-015 | **Import with an `Identifier` that already exists** | `--on-conflict skip` skips the row and counts it; `update` applies the non-empty fields of the CSV over the existing issue (with history); `fail` (default) aborts the import. In all three cases the final report lists `created`/`updated`/`skipped`/`failed` with numbers, and `--dry-run` produces the same report without writing. |

### 4.5 Fractional ranking strategy

Constants in `domain/constants.py`: `RANK_GAP = 1024.0`, `RANK_EPSILON = 1e-4`. The same function is
used for `sort_order` (backlog), `board_order` (board column, per `(team_id, state_id)`) and
`sub_issue_sort_order` (per `parent_id`).

```
rank_between(prev: float | None, next: float | None) -> float
  prev is None and next is None  -> RANK_GAP                 # first item
  prev is None                   -> next - RANK_GAP          # insert at the beginning
  next is None                   -> prev + RANK_GAP          # insert at the end
  otherwise                      -> (prev + next) / 2        # insert in the middle

needs_rebalance(prev, next) -> bool
  abs(next - prev) < RANK_EPSILON

rebalance(scope)  # scope = (team_id, state_id) | parent_id | team_id
  UPDATE ... SET col = (ROW_NUMBER() OVER (ORDER BY col, number)) * RANK_GAP
  # one statement per column, inside the same transaction as the move
```

Rules: a `move` that needs rebalancing does it **before** computing the new order and reports
`rebalanced: true`; rebalancing never changes the relative order (it uses `ORDER BY col, number` to
break ties); values are always finite and positive (the first one may end up with values <
`RANK_GAP` after inserts at the beginning, and that is correct: only the order matters).

## 5. Flow

### 5.1 Layer architecture

The structure is the one in SPEC-000 §4.3 (`domain/`, `ports.py`, `app/`, `adapters/sqlite/`, `cli/`,
`api/`, `web/`, `config.py`). Dependencies in a single direction:

```
┌──────────────────────────────────────────────────────────────────────────────┐
│ ENTRY (three interchangeable edges over the same use cases)                  │
│  cli/ (Typer)        api/ (FastAPI, /api/v1)      web/ (Jinja2 + htmx)       │
│  hifa <cmd> --json   /api/v1/*  /healthz         /{team}/board /{team}/list  │
└───────────────┬──────────────────────┬──────────────────────┬───────────────┘
                └──────────────────────┼──────────────────────┘
                                       ▼
┌──────────────────────────────────────────────────────────────────────────────┐
│ app/  use cases, transactions (UoW), composite invariants                    │
│  issues · teams · labels · projects · cycles · boards · search · transfer    │
└───────────────────────────────┬──────────────────────────────────────────────┘
                                ▼
┌──────────────────────────────────────────────────────────────────────────────┐
│ domain/  entities, enums, ranking, identifier, rules, errors (no IO)         │
│ ports.py  Protocols: repos, UnitOfWork, Clock, IdGen                         │
└───────────────────────────────┬──────────────────────────────────────────────┘
                                ▼
┌──────────────────────────────────────────────────────────────────────────────┐
│ adapters/sqlite/  connection · uow · migrate · repos · reads                 │
└───────────────────────────────┬──────────────────────────────────────────────┘
                                ▼
                        SQLite (WAL) — hifa.db
```

Hard rules (SPEC-000 A1-A3): `domain/` does not import infrastructure, `app/` does not write SQL,
only `adapters/sqlite/` touches the database. `ports.py` is the contract between `app/` and
`adapters/`.

### 5.2 Nominal v1 flow

```
1. hifa init            → migrates (user_version 3) and seeds (D-013)
2. hifa issue add       → MAX(number)+1 inside BEGIN IMMEDIATE → identifier ENG-1
3. hifa issue list      → AND filters, deterministic order, keyset cursor (1-200)
4. hifa board           → columns by position, board_order inside the column
5. hifa search          → FTS5 (backend fts|like|none) with snippet
6. hifa serve           → uvicorn 127.0.0.1:7777, views + /api/v1
7. hifa doctor          → quick_check, FKs, counts, FTS, cycles; exit 0/1/2/3
```

### 5.3 Identifier generation under transaction

```
with uow.write():                            # BEGIN IMMEDIATE (SPEC-030)
    number = issue_repo.next_number(team.id) # SELECT COALESCE(MAX(number),0)+1 (SQL-1)
    identifier = f"{team.key}-{number}"
    issue_repo.insert(..., number=number, identifier=identifier)
```

Properties: the write lock is taken before reading, so two processes never get the same
number; if the INSERT fails, the transaction rolls back; on `UNIQUE(team_id, number)` the use case
retries up to 3 times recomputing the number (D-018: the retry does not live in the contextmanager of
the UoW). With no physical delete (D-015), `MAX(number)+1` never recycles a number. `team set-key`
recomputes `identifier` from `key || '-' || number` without touching `number`.

### 10.1 Open Questions

1. **Final name and availability on PyPI.** `hifa` is provisional; it was not verified whether the
   name is free on PyPI nor whether it collides with an existing binary. It affects `pyproject.toml`,
   the entrypoint and the package name (`hifa` vs `hifa-cli`).
2. **Multi-workspace in v1.** The schema supports N rows in `workspace` and every table hangs off
   `workspace_id`, but the CLI does not expose `workspace add/switch`. Do we keep a single row
   forced by `init` or do we add the global flag `--workspace`?
3. **Non-ISO date format in CSV import.** It was decided to reject everything that is not `YYYY-MM-DD`
   (EC-014). If files with `dd/mm/yyyy` show up, an explicit `--date-format` would be needed.
4. **Backup as a first-class command.** The backup before migrations uses `VACUUM INTO`, but there is
   no `hifa backup`/`hifa restore` with rotation. v1 or post-v1?
5. **`branch_name` and branch format.** The column exists and `team` has no `branch_format`. Is
   `eng-123-title-slug` generated automatically or does it stay a manual field?
6. **Order of `priority = 0` on the board.** It was assumed "No priority" at the end of the listing.
   Is it also kept on the board and in the export, or does the board show it first?
7. **Repo license.** Not decided (MIT vs Apache-2.0). It affects the README, `pyproject` and the header of
   the files.
8. **Vertical verbs with no counterpart in SPEC-050 (seam 001↔050).** The Gherkin of
   `acceptance/001-mvp-v1/` covers behavior that today **has no command** in the normative tree of
   SPEC-050 §2.5: team key rotation (REQ-F006), add/remove of workflow states
   (REQ-F008/F009), milestones (REQ-F027), resolving and editing comments (REQ-F022), reading
   history, the sub-issue tree and `blocked_by` (REQ-F020/F021/F028), the board as a command
   (REQ-F018) and `--allow-overlap` in `cycle create` (REQ-F026). The affected scenarios are
   written at domain level ("the key is changed…", "the state is added…", "I query the board…")
   so as not to invent CLI surface, and the tasks implement the use case in `app/`. **Closing
   this requires a contract change in SPEC-050** (`team set-key`, `state add|delete`,
   `milestone add`, `comment resolve|edit`, `issue history|tree|blocking`, `hifa board`,
