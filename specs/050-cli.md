# SPEC-050 — CLI

## 1. Responsibility and boundaries

**Does:** defines the complete command surface of `hifa` (Typer), context resolution
(`--db`, `.hifa.toml`, default team), the output contract (table / `--json` / `--quiet`),
the exit code table, and the mapping of domain errors to those exit codes. It is the entry
edge for humans and for scripts.

**Does NOT do (explicit):**
- It holds no business logic and no invariants: every command is *parse → call a use case →
  format*. Computing issue numbers, validating transitions or building SQL here is forbidden.
- It opens no SQLite connections and runs no SQL: it receives an already built `UnitOfWork` (`hifa.adapters.sqlite`).
- It does not print on its own (A6): every `stdout`/`stderr` write goes through `hifa/cli/output.py`.
- It brings up no network, sockets or HTTP, **except** `hifa serve` (A4, REQ-N004). No other command imports
  `fastapi`, `uvicorn` or `httpx`.
- It implements no authentication, telemetry, auto-update or remote sync.
- It defines neither the import/export formats (SPEC-080) nor the FTS search text (SPEC-090).

## 2. Public contract

### 2.1 Entrypoint and layout

```toml
# pyproject.toml
[project.scripts]
hifa = "hifa.cli.main:app"
```

```python
# src/hifa/cli/main.py
import typer

app = typer.Typer(
    name="hifa",
    no_args_is_help=True,
    add_completion=True,
    context_settings={"help_option_names": ["-h", "--help"]},
)

# registered sub-apps (one per file under cli/commands/)
app.add_typer(team_app, name="team")
app.add_typer(issue_app, name="issue")
app.add_typer(state_app, name="state")
app.add_typer(project_app, name="project")
app.add_typer(cycle_app, name="cycle")
app.add_typer(member_app, name="member")
app.add_typer(label_app, name="label")
app.add_typer(db_app, name="db")
```

```
src/hifa/cli/
├── main.py            # root app, global callback, sub-app registration
├── context.py         # CliContext: resolves db/team/member/color/format
├── output.py          # render_table, render_json, render_quiet, echo_err, color
├── errors.py          # domain error -> exit code + mensaje; handler global
├── refs.py            # parseo de refs: KEY-123, ULID, nombre de estado, prioridad
└── commands/
    ├── init.py  doctor.py  serve.py  search.py  transfer.py
    └── team.py  state.py  issue.py  project.py  cycle.py  member.py  label.py  db.py
```

`hifa.cli` may **only** import: `hifa.app.*`, `hifa.domain.*` (types and errors), `hifa.config`,
`hifa.adapters.sqlite.uow`, `typer`, `rich` **no** (forbidden: the table is drawn by hand in
`output.py`), stdlib. Importing `hifa.api.*` and `hifa.web.*` is forbidden; `hifa serve` imports
`uvicorn` **inside** the command function (deferred import) so that the rest of the CLI
works without the `[web]` extra (A5).

### 2.2 Global options and context resolution

Declared in the root callback. They must come **before** the subcommand:

| Option | Type | Default | Effect |
|---|---|---|---|
| `--db PATH` | path | see 2.2.1 | SQLite file to use |
| `--team TEXT` | str | see 2.2.2 | default team for this invocation |
| `--member TEXT` | str | see 2.2.3 | default member (`--mine`, `--assignee` with no argument) |
| `--json` | flag | off | JSON output (2.4.3) |
| `--quiet` / `-q` | flag | off | minimal output (2.4.4) |
| `--no-color` | flag | off | disables ANSI |
| `--no-input` | flag | off | never ask for confirmation: without a TTY, implicit `--yes`; with a TTY and confirmation required, exit 2 |
| `--version` | flag | — | prints `hifa <version>` and exits 0 |
| `-h/--help` | flag | — | help and exit 0 |

`--json` and `--quiet` together are contradictory: exit **2** with code `invalid_option`, without
writing anything to `stdout`.

`--db`, `--team` and `--member` are **also** accepted at leaf-command level (after the
subcommand); the leaf value wins over the global one. No other global option is duplicated.

#### 2.2.1 Database file resolution

The precedence table is the one in **SPEC-100 §2.2** (5 sources, `source` included: `flag`, `env`,
`file`, `xdg`, `home`) and is not repeated here. Edge rules:

1. `--db` (global or leaf) always wins; if it is empty it is ignored.
2. `HIFA_DB` wins over the file and over XDG.
3. `[workspace] db` in `.hifa.toml` is resolved **relative to the file's directory**; if the TOML
   does not declare `db`, the path is `<dir of .hifa.toml>/.hifa/hifa.db` (project-local, never XDG).
4. With no file in the tree: `$XDG_DATA_HOME/hifa/hifa.db` and, if the variable is unset, `source="home"`.

The file is resolved to an **absolute** path before opening it; the parent directory is created with
`0o700` if missing. If the file does not exist: read/write commands fail with exit **3**
and code `database_not_found` (they never create an empty database by accident); `hifa init` and
`hifa db migrate` do create it.

#### 2.2.2 Default team resolution

Order, first non-empty value wins. A value counts as **empty** if it is `""`, `null` or absent.

1. `--team` (global or leaf)
2. `HIFA_TEAM`
3. `[cli].default_team` in `.hifa.toml` (SPEC-100 §2.3; file default: `[team].key`)
4. If the workspace has **exactly one** non-archived team: that team
5. If it has 0 or ≥2: exit **2**, code `missing_context`, message
   `team required: use --team, HIFA_TEAM or [cli].default_team in .hifa.toml`

#### 2.2.3 Default member resolution

1. `--member`
2. `HIFA_MEMBER`
3. `NULL`

`.hifa.toml` does **not** declare a member (SPEC-100 §2.3): there is no `[defaults] member` and no
`[cli].default_member`. If the value matches no member (by `id`, `display_name` or `email`,
case-insensitive): exit **3** `not_found` with `field: "member"`. A member is never invented.

#### 2.2.4 `.hifa.toml` discovery

It is searched from `Path.cwd()` upwards to the filesystem root, at most 32 levels; the first one
found wins (SPEC-100 §2.4). The file format is **the one in SPEC-100 §2.3**, a single one:

```toml
[workspace]
name = "Ginkelte"
db = ".hifa/hifa.db"          # relativo al directorio del .hifa.toml
url_key = "ginkelte"

[team]
key = "ENG"
name = "Engineering"

[cli]
default_team = "ENG"

[web]
host = "127.0.0.1"
port = 7777
```

All keys are optional; an unknown section or key is ignored with a warning
(`unknown_key`), a value of the wrong type is exit 2 `invalid_config`. `hifa init` writes this
file according to SPEC-100 §4.2 R13 (only if it does not exist in the tree, or with `--force`).

and this table is fixed in the next bump (D-012).

Conventions:

  one use case = one `uow.write()`** (SPEC-040 R1). `issue label` with N labels is N commands

- `--sort`, `--reverse`, `--limit` and `--cursor` map onto the `ListFilters` fields and the keyset
  contract of **D-011** (see §4 R7/R8); the CLI does not define its own filter object.

### 2.4 Output contract

Rules that apply to **all** commands (A6):

- `stdout`: data only. `stderr`: diagnostics only (warnings, counts, errors, prompts).
- A command that mutates and succeeds writes the affected object to `stdout` (table or JSON depending
  on the format); never a message such as "OK".
- ANSI codes only if `stdout.isatty()` **and** `NO_COLOR` is not defined **and** `TERM != "dumb"`
  **and** `--no-color` was not passed. `--json` and `--quiet` imply no color.
- Table width: `min(terminal_width, 120)`; without a TTY: `120`. Two columns are truncated, both with
  `…` (U+2026, reserving 1 cell): `TITLE`, and `BODY` in the `issue comment` table, which keeps **60**
  cells and renders every newline as a space, so a markdown body stays on one row. The rest is never
  truncated.

#### 2.4.1 Table (default format)

UPPERCASE header, no borders or separators, two spaces between columns, numbers
right-aligned, text left-aligned. Priority is abbreviated to a single character:

| `priority` | 0 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|---|
| glyph | `–` (U+2013) | `U` | `H` | `M` | `L` |

#### 2.4.3 `--json`

A single JSON document per invocation, UTF-8, `indent=2`, `ensure_ascii=False`, with a trailing
newline.

**One list shape.** Every command that returns a collection emits an object whose only key is
`items`:

```json
{
  "items": [ /* objetos */ ]
}
```

`next_cursor`, `has_more` and `total_estimate` are **not** part of that shape. They exist only in
commands that paginate with `--cursor`, which in v1 is `issue list` alone (§2.5.3); that command
emits the same object plus the three cursor keys:

```json
{
  "items": [ /* objetos */ ],
  "next_cursor": "eyJ2Ij...dHki..." ,
  "has_more": true,
  "total_estimate": null
}
```

`next_cursor` is `null` when `has_more` is `false`. `total_estimate` is always `null` in v1
(the total is not counted: `COUNT(*)` over 10 000 rows would break REQ-N008) and exists only so that
the paginated envelope does not change shape in v2.

`total_estimate` is written by the **edge**, as a constant: `IssuePage` of SPEC-030 §2.6 has
`items`, `next_cursor` and `has_more` and no total field, and no use case counts the filtered set
(SPEC-040 R18). The key therefore means **"unknown", never "zero"**: a consumer must not read
`total_estimate == null` as an empty result — `items` says that — and a consumer must not read
`0` as anything, because the command never emits `0`. The same key is `null` on every page, including
the last one and the empty one; a value other than `null` is out of contract in v1.

The base shape is the one `team list`, `project list`, `cycle list`, `member list`, `label list` and
`issue attach --list` print, and the one the implementation emits
(`output.emit(rows, json_obj={"items": rows})`): one record per element for `--quiet`, one row per
element for the table. Declaring the cursor keys on every list announced a pagination those
commands do not have (D-031).

`hifa search --json` returns the envelope defined in **SPEC-090 §2** (authority for the search
contract): `{hits: [{issue, snippet, score}], total, has_more, backend, took_ms}`. This document
does not redefine that envelope; if it changes, SPEC-090 changes and the reference here is adjusted.

**One command returns a two-key envelope, and it is the only one:** `issue label` and `issue unlabel`
emit the issue **and** the label the write removed, because a `singleSelect` group replaces a label and
the issue object cannot say which one it lost (D-061, SPEC-040 R10):

```json
{
  "issue": { /* the canonical Issue of §2.4.2, after the write */ },
  "replaced": { "id": "01JCV5AAA", "name": "High", "color": "#EB5757" }
}
```

`replaced` is `null`, or the three fields of the label entity that `AddLabelResult.replaced` returns
(SPEC-040 §2.2) — `id`, `name` and `color`, the same three the `labels[]` element of §2.4.2 carries, so
a client that removes the replaced chip reads one shape for both. No other member of the `Label`
travels here: `team_id`, `parent_id`, `is_group`, `group_type`, `description` and `retired_at` are
readable through `label show --json` (§2.5.4).

It is `null` when nothing was replaced — which is every `issue unlabel`, every `issue label`
outside a `singleSelect` group, every `issue label` of a group whose sibling the issue did not carry,
and the idempotent no-op. The table output is unchanged (one row with the columns of `issue list`,
§2.4.1) and `--quiet` prints the `identifier`; the envelope is the `--json` shape of those two verbs
alone, and every other mutation keeps the single object of §2.4.2.

#### 2.4.4 `--quiet`

One line per affected record, no header, no color, no diagnostics:

- read commands: the identifier (`ENG-123`) or `id` if the entity has no identifier;
- `issue create`: the `identifier` created;
- mutation commands: the affected `identifier`, or — when the record it wrote has none — its `id`
  (`issue comment` writes a `Comment`, which carries an `id` and no identifier);
- `label add|update|archive|show`: the label's `id` — a `Label` has no identifier (D-061);
  `label list`: one `id` per line;
- `hifa db migrate`: nothing on `stdout`;
- commands with no record (e.g. `db vacuum`): nothing.

#### 2.4.5 Errors on `stderr`

Without `--json`: one line `hifa: <message>` and, if there is a `field`, ` (field: <field>)`.
With `--json`: the same envelope as the API (SPEC-060 §6.3) on `stderr`, and an empty `stdout`:

```json
{"error": {"code": "not_found", "message": "issue 'ENG-999' does not exist", "field": "issue", "details": null}}
```

The four keys are the envelope's and none is optional (SPEC-060 §6.3): `field` and `details` are always
present, `details` `null` unless a refusal reports several validation errors, and this 404 renders it
`null` because the resource already travels in `field` and the key in `message` (D-062).

`field` is read from the exception and never built at this edge (§5.3): `Validation`, `Conflict`,
`InvalidTransition` and `InvalidOption` carry the input field that was refused (`title`, `ref`, `parent`,
`description`), and `NotFound` carries its `resource` — the noun of **what does not exist** — through
the derived accessor of SPEC-020 §2.6. That is what keeps the two 404s of a label apart on both edges: a
`LABEL` reference that resolves nowhere is `not_found` with `field: "label"` (the label is missing),
while a label the issue exists without wearing is `not_found` with `field: "label_link"` (the label is
there and the link is not). The two edges publish the same value for the same input, because both read
the same accessor.

The exit code never depends on the output format (A7).
### 2.5 Command tree (normative)

Conventions for this section: `REF` = `identifier` (`ENG-123`) or ULID; a state `NAME` is
case-insensitive within the resolved team. A label `NAME` is case-insensitive too, and its scope is the
scope of the reference (`LABEL_AMBIGUOUS` when it cannot be decided): **issue-scoped** references —
`issue label` and `issue unlabel` — resolve it in the **issue's** team and then in the workspace, so
the issue's team is the tie-breaker; the **list filter** `issue list --label` (§2.5.3.1) has no issue
and uses the **command's** team — `--team`, else the resolved default of §2.2.2 — and then the
workspace; **catalogue-scoped** references — `label show|update|archive` — resolve it over the whole
workspace, **retired rows included** (they are the rows `label archive --undo` and a rename of a
retired label are asked for, and `label list` hides them unless `--all` because that is a render and
not a resolution), with `LABEL_AMBIGUOUS` (exit 2, `field: "ref"`) when two teams share it; `--yes`
skips confirmation; every mutation accepts `--json` and `--quiet`.

#### 2.5.2 `team`

| Command | Arguments / flags | `--json` | Exit |
|---|---|---|---|
| `hifa team create KEY NAME` | `KEY` and `NAME` positional, both required; `--icon TEXT` (emoji), `--color TEXT` (`^#[0-9A-Fa-f]{6}$`), `--description TEXT`, `--timezone TEXT` (default `America/Santiago`), `--visibility {public,private,restricted}` | `Team` | 0,2,4 |

`create` is the **only** form that creates a team: there is no `team add` alias and no second
handler. (The previous revision of this table declared `team add --key --name`; it was never
implemented and is replaced here — D-030.) The command is *parse → delegate*, nothing else:

- `KEY` is validated by `create_team` through `identifier.validate_key` (SPEC-020 §2.2), **not** at
  this edge: the key is normalized first (`strip()` + `upper()`, so `ops` and `OPS` are the same
  team) and then matched against `KEY_PATTERN`. A key outside the pattern ⇒ exit 2,
  `Validation(rule="TEAM_KEY_INVALID")`. The CLI does not re-declare the pattern, so it has one
  owner.
- A `KEY` that already exists in the workspace ⇒ exit 4, `Conflict(rule="UNIQUE_TEAM_KEY")`
  (SPEC-040 §6: that is the only duplicate-team code, and the CLI invents no other).
- The call is `create_team(uow, CreateTeam(key=KEY, name=NAME, icon=…, color=…, description=…,
  timezone=…, visibility=…), actor)` (**SPEC-040 §2.2**, REQ-F040-14): **one** transaction that
  creates the workspace if it is missing, the team and its **7** default states. The CLI creates no
  state, invents no default and runs no SQL; the seeded states are those of SPEC-100 §2.5
  `DEFAULT_STATES`. Consequence, and the reason it is contract: a team either exists with a usable
  workflow or it does not exist at all — there is no half-created team to repair by hand.
- `CreateTeam` has no `parent`, `estimation_type` or `cycles_enabled` field today, so the command
  offers no flag for them. A flag the use case cannot carry is not declared at this edge (D-012).
- `list` orders by `key` **ASC** — not by name, not by `created_at` — and prints `KEY`, `NAME` and
  `ISSUES`, where `ISSUES` = `open_count + closed_count` of `v_team_progress` (SPEC-010 §3.3), that
  is every issue with `archived_at IS NULL AND trashed = 0`. A team with no issues has no row in the
  view: its count is `0`, not an error and not a blank. `--all` includes archived teams, flagged in
  the `ARCHIVED` column. `--json` emits `{items: Team[]}` in the same order, each item carrying
  `issues_count` as an **additive** field (default `0`, D-026).
- `show` accepts `KEY` in any case (`ops`, `Ops`, `OPS` normalize to the same team); an unknown key
  ⇒ exit 3, `NotFound(team)`. Without `KEY` it shows the team resolved by 2.2.2 and exits 2
  `missing_context` if that resolution fails.

`team show --json` adds `progress: {open_count, closed_count, urgent_open}` read from
`v_team_progress` (SPEC-010 §3.3) and `states: State[]` sorted by `position` ASC.
`team archive` is **not declared**: `archive_team` does not exist and is deferred with `update_team`
(D-031). The three revisions of this spec described it in mutually exclusive terms — open issues as
`Conflict`/exit 4 here, as `Validation(TEAM_HAS_OPEN_ISSUES)`/exit 2 in SPEC-040 §2.2/§6, and
re-archiving as idempotent/exit 0 in R5 — so the surfaces were removed instead of picking a winner
by accident. The row returns with the use case, in the revision that settles those semantics.

Normative notes:

- `create`: the title arrives positionally **or** through `--title`, never both (both ⇒ exit 2,
  `field: "title"`); neither ⇒ exit 2. `--description-file -` reads `stdin`.
- `comment`: the body arrives positionally **or** through `--body-file`, never both (both ⇒ exit 2,
  `field: "body"`); neither is exit 2 `field: "body"`, unless `stdin` is not a TTY, in which case it is
  read as the body — the same convention `create --description-file -` already uses. There is no
  `--body` flag: `--body -` in `REQ-F022` is this row, and §2.5 is a closed tree (R17).
- `create` without `--state` uses the team's workflow state with `is_default = 1`; if there is none,
  the one with the lowest `position`.
- `list --mine` = `assignee` = resolved member (2.2.3); no member ⇒ exit 2 `missing_context`.
  `--mine` is sugar for `--assignee <that member>`, so it is **not** combined with `-a/--assignee` or
  with `--unassigned`: either pair is exit 2 `invalid_option` (`field: "assignee"`), because both
  operands cannot be true at once and the edge does not silently pick one. `-a/--assignee` accepts a
  member id, display name or email (the §2.2.3 vocabulary, case-insensitive) and resolves to
  `assignee_id`; an unknown member is exit 3 `not_found` (`field: "member"`), never a silent empty
  list — the field names the resource that is missing, which is the `member` §2.2.3 and SPEC-040 §5.4
  raise, not the flag that carried the value.
- `--open` (default) ⇒ `is_open = 1`; `--all` ⇒ no `is_open` filter; `--archived` ⇒
  `archived_at IS NOT NULL`; `--trashed` ⇒ `trashed = 1` (implies `--all`). `--archived` and
  `--trashed` together ⇒ exit 2. The four flags are two independent axes and compose: the full matrix,
  with the `ListFilters` field each cell sets, is §2.5.3.1.
- `edit` is the **only** verb of `update_issue` (SPEC-040 §5.4): there is no `hifa issue update` and no
  alias — the tree of §2.5 is closed (R17), so an undeclared verb is exit 2 `invalid_option`. There is
  one flag per field §5.4 resolves: `--title`, `--description`/`--description-file`, `--priority`,
  `--state`, `--assignee`, `--project`, `--milestone`, `--cycle`, `--parent`, `--estimate`, `--due`.
  An absent flag leaves the field `UNSET`; `--clear-<field>` sends `None` and writes `NULL`. Labels are
  not edited here: `issue label` / `issue unlabel` own `issue_label`.
- `edit` with no flags at all ⇒ exit 2 `no_changes`, before opening the database. With flags whose
  values equal the stored ones the command exits **0**, writes no history row and leaves `updated_at`
  untouched (SPEC-040 §5.4 step 6): it is not `no_changes`, which is reserved for the empty invocation.
- `edit` exit codes: **0** written, or nothing to change; **2** the first `Validation` in the resolution
  order of §5.4 step 4 — `TITLE_EMPTY`/`TITLE_TOO_LONG` (`field: "title"`), `PRIORITY_OUT_OF_RANGE`,
  `MEMBER_INACTIVE`, `PROJECT_TEAM_MISMATCH`, `MILESTONE_PROJECT_MISMATCH`, `CYCLE_TEAM_MISMATCH`,
  `CYCLE_COMPLETED`, `PARENT_SELF`/`PARENT_TEAM_MISMATCH`/`PARENT_CYCLE`/`PARENT_DEPTH_EXCEEDED`,
  `ESTIMATE_*`, `DUE_DATE_FORMAT`,
  `STATE_TEAM_MISMATCH`, `STATE_ARCHIVED`, `CLOSE_WITH_OPEN_CHILDREN`, `ISSUE_TRASHED`; **3** the
  issue, state, member, project, milestone, cycle or parent does not exist; **4** only `DB_BUSY` /
  `DB_READONLY` / `READ_ONLY_UOW` (no edited field is unique); **5** `ISSUE_ARCHIVED` — the issue has
  `archived_at` not null (SPEC-040 §6, R20) and no field is written.
- **`label` and `unlabel` are N transactions, and the CLI says so honestly.** `LABEL...` is one
  `AddLabel`/`RemoveLabel` per label, **one `uow.write()` each** (SPEC-040 R1; GAP-05): there is no
  multi-label atomicity in v1, so a command whose third label is refused has already written the first
  two. The exit code is the one of the **first failure**, the error line on `stderr` names that label,
  and `stdout` stays empty for that invocation — no partial `Issue` and no partial envelope, because a
  caller reading `stdout` must not mistake a half-applied command for a whole one. `--json` prints the
  error envelope of §2.4.5 on `stderr` and nothing on `stdout`. A label repeated in the same
  invocation (`bug bug`, or `bug,bug`) is one label: the values are de-duplicated preserving their
  order before the first call, so the command never pays a second transaction for a value it already
  wrote.
- **`label` resolves names in the issue's team, and there is no `--team` to move it.** The order is
  the one `AddLabel` declares (SPEC-040 §2.2 and §5.6, and §2.5's conventions): a ULID resolves
  directly, a name resolves to the label of the **issue's** team and then to the workspace one — two
  levels, and the issue's team is the tie-breaker, so no name is ever ambiguous here. A label of
  another team is exit 2 `validation_error`, `field: "label"` (`LABEL_TEAM_MISMATCH`), and a name that
  exists nowhere is exit 2 `LABEL_NOT_FOUND` unless `--create` is given; a ULID that exists nowhere is
  exit 3 (`not_found`, `field: "label"`). The verb publishes no `--team` because the issue already
  names the team the label has to belong to — a flag that could only contradict it is not a feature,
  and `--team` at leaf level stays the global option of §2.2, which this verb does not consult.
- **`--create` is the one creation path of this verb, and it creates in the issue's team.** The label
  is inserted in the same transaction as the link (`AddLabel(create_if_missing=True)`, SPEC-040 R22)
  with `is_group = 0`, `group_type = NULL`, `parent_id = NULL`, `description = NULL` and the `--color`
  it was given (`#6B6F76` by default, the same default as `label add --color`). A name that already
  resolves at either level is used and nothing is created. `--color` without `--create` is exit 2
  `invalid_option`, `field: "color"`: a color that would be written nowhere is a typo, not a request.
  A group, a workspace label or a described label is `hifa label add` (SPEC-050 §2.5.4) — this verb
  creates the cheap label, not the catalogue.
- **The answer carries the replacement.** `--json` is the two-key envelope of §2.4.3: `issue` is the
  canonical `Issue` after the write and `replaced` is the label a `singleSelect` group took off the
  issue, or `null` (SPEC-040 R10). The table prints one row with the columns of `issue list` and
  `--quiet` prints the `identifier`; neither has a column for `replaced`, because the issue's `LABELS`
  cell already shows the resulting set and the replacement is a fact about the call. Exit codes: **0**
  written or already present; **2** `LABEL_NOT_FOUND`, `LABEL_TEAM_MISMATCH`, `ISSUE_TRASHED`,
  `COLOR_FORMAT`, `--color` without `--create`; **3** the issue or a ULID label does not exist;
  **4** `LABEL_RETIRED` (a retired label is not attachable, SPEC-020 R8) and `UNIQUE_LABEL_NAME`
  (`--create` racing another writer); **5** `ISSUE_ARCHIVED` (R20).
- **`unlabel` removes one link per call and never a sibling.** A label the issue does not carry is
  exit 3 `not_found` with `field: "label_link"` (SPEC-040 R10) — not the label's `id`, because the label
  may well exist; the pair is what is missing, and `field` names it. The `--json` envelope of §2.4.5
  carries `code`, `message`, `field` and `details`, and the label-vs-link distinction SPEC-040 makes in
  `details.resource` **is** observable at this edge through `field`, which is that same resource
  (SPEC-020 §2.6): a **reference** that resolves nowhere answers `not_found` with `field: "label"`, and
  a label the issue does not wear answers `not_found` with `field: "label_link"`. An unknown ref is
  exit 3 here — a **name** that resolves at neither level too, where `issue label` answers it with exit
  2 `LABEL_NOT_FOUND` (SPEC-040 §2.2, §5.6). `replaced` is always `null` (detaching is not a group
  decision), and a retired label is **not** refused here: taking a retired label off an issue has to
  stay possible, or a retire would strand the chips it left behind.
  Exit codes: **0** the link is gone; **2** `ISSUE_TRASHED`; **3** the issue, the label or the link
  between them does not exist; **5** `ISSUE_ARCHIVED` (R20).
- `--state` on `edit` is a **move**: the issue is appended to the end of the target column (R8) because
  `UpdateIssue` carries no position. A caller that needs a specific place uses `issue move`. An anchor
  flag on `edit` (`--before`, `--after`) is exit 2 `invalid_option`.
- `move --before REF` ⇒ `MoveIssue(position="before", before_id=REF, after_id=None)`; `--after REF` ⇒
  `MoveIssue(position="after", after_id=REF, before_id=None)` (SPEC-040 §2.1, `MoveIssue.before_id` /
  `after_id` are reference anchors). The
  `board_order` is computed by `move_issue` with `ranking.between` (SPEC-040 R8) and rebalances only if
  `between` raises `RANKING_EXHAUSTED` (SPEC-040 R9). The CLI **does not** send numeric positions. With
  `--before` and `--after` together ⇒ exit 2. With neither ⇒ `position="last"`.
- `move` exit codes: **0** moved, or already in the target state and already last (no write, no history
  row); **2** `STATE_TEAM_MISMATCH`, `STATE_ARCHIVED`, `CLOSE_WITH_OPEN_CHILDREN` (terminal target with
  open sub-issues), `ISSUE_TRASHED`, `POSITION_NEIGHBOR` (anchor that does not exist in the target
  column, or belongs to another team or another state), `RANKING_EXHAUSTED`, or `--before` together with
  `--after`; **3** the issue or the state name/ULID does not exist (the message names the state the user
  typed); **5** `ISSUE_ARCHIVED`. Nothing is written before the validations of SPEC-040 §5.2 step 5.
- `move` prints **one row** with the columns of `issue list` (§2.4.1); `--json` prints the canonical
  `Issue` of §2.4.2 **after** the write — with the new `state`, `board_order` and the derived milestone
  (`started_at`/`completed_at`/`canceled_at`). No key is added: there is no `rebalanced` field, because
  the rebalance happens inside `move_issue` and is not a visible outcome (SPEC-040 §5.2 R9).
  `--quiet` prints the `identifier`.
- `delete` is *soft*: `trash_issue` sets `trashed = 1` and `updated_at`. **There is no physical delete**:
  there is no `--hard`, no cascade, no `DELETE FROM issue` (D-015; SPEC-030 R11). Compaction is
  `hifa db vacuum`, which deletes no logical rows. `--yes` avoids the prompt; without it, and with an
  interactive TTY, confirmation is requested (§4 R6).
- `archive` exit codes: **0** archived, or already archived — a no-op that writes nothing and moves
  neither `archived_at` nor `updated_at` (R12); **2** `CLOSE_WITH_OPEN_CHILDREN` (parent with open
  sub-issues), `ISSUE_TRASHED` (an issue in trash is restored first) and `confirmation_required`
  (`--yes` missing on a TTY, or `--no-input`); **3** the issue does not exist. The confirmation is asked
  **before** the use case runs — this edge holds no business logic and does not read the database (§1) —
  so `issue archive` on an already archived issue still asks and then exits **0** without writing. It
  changes no state: the issue keeps its `state_id` and leaves the listings by `archived_at` alone.
  `--undo` runs `restore_issue` on the same reference and is the only way back.
- `restore` exit codes: **0** restored, or nothing to restore (neither `archived_at` nor `trashed` set:
  no-op, exit 0); **2** `invalid_option` for `--hard` (below); **3** the issue does not exist. It clears
  `archived_at` first and `trashed` after (SPEC-040 §5.5) and never prompts: undoing is not destructive.
- `--hard` is not a flag of `archive`, `restore` or `delete`: there is no physical deletion (D-015,
  SPEC-030 R11), so the flag is unknown ⇒ exit 2 `invalid_option` and the row is untouched.
- Every write verb of §2.5.3 also exits **4** when SQLite is busy or the file is read-only
  (`DB_BUSY`, `DB_READONLY`) or when the UoW is a read one (`READ_ONLY_UOW`), and **6** when the layer
  raises `HifaError` (`RANKING_DEGRADED`, `UOW_NESTED`, `HIFA_ERROR`) — SPEC-040 §6. Those two codes are
  not repeated in the exit set of each verb: the lists above name the codes the verb itself decides,
  plus `6` for `move`, whose `RANKING_DEGRADED` is the one internal error a user can reach.
- `edit`, `move`, `archive` and `restore` are one `uow.write()` against the resolved SQLite file: none
  opens a socket and none needs `hifa serve` running (A4, R9). Their `--json` envelope, exit codes and
  table output are the same with no server up.
- `relate` writes **one** row and prints it as the canonical `Relation` of §2.4.2 — the five stored
  columns, with `type` one of the four values and never `blocked_by` (SPEC-020 §2.1, D-046). The same
  object is what `issue show --with relations` prints for each row of the edge, from either end: the
  directed reading of the pair is the web read model's (SPEC-070 §2.3.4) and the CLI emits no
  `direction` (§2.4.2). `TYPE`
  accepts `blocked_by` as the input alias of the reverse `blocks`: `hifa issue relate ENG-2 blocked_by
  ENG-1` stores `(ENG-1, ENG-2, blocks)`, and `--undo` accepts the alias too and deletes that same row.
  A symmetric type is stored in one canonical order (D-045), so writing the same pair again from the
  other end is the same relation, not a second row.
- `relate` exit codes: **0** written; **2** `RELATION_SELF` (`OTHER` == `REF`),
  `RELATION_WORKSPACE_MISMATCH` (the two issues live in different workspaces) or `COMMAND_FIELD` (`TYPE`
  outside the five accepted tokens); **3** one of the two references does not exist; **4**
  `RELATION_DUPLICATE` — the pair already carries that type, in either order (D-047).
  `--undo` of a relation that does not exist is exit 3 `not_found` with `resource: "relation"`.
- `relate` is the **only** verb that writes an edge, and its `--undo` is the only way back: there is no
  `issue link`, no `issue unlink` and no alias for either, because the tree of §2.5 is closed (R17) and
  an undeclared verb is exit 2 `invalid_option`. The reverse direction is not a second verb either —
  `TYPE` carries it as `blocked_by`, which is the input alias of the reverse `blocks` (D-046).
- The `field` of a `relate` refusal is the one SPEC-020 §2.5 publishes, not a name chosen here: `type`
  for `COMMAND_FIELD` — the positional outside the five accepted tokens — and `related` for
  `RELATION_SELF` and `RELATION_WORKSPACE_MISMATCH`. A reference that does not exist carries `ref`
  (§6). The command, the parser and the error share the one name `type`, which is also the `type` key of
  `Relation` (§2.4.2), so a caller switching from CLI to HTTP reads the same field.
- `relations` prints **one row per stored edge that touches `REF`**, read from `REF`'s side, and never
  two rows for one edge: the pair has one row whichever end it was written from (D-045). `REF` is
  resolved once by `issue_detail` (§2.3), which already returns the edges as `(IssueRelation,
  IssueListItem)` pairs — the stored row plus the far end's list item — so the table costs no second
  query and no N+1. An unknown or trashed `REF` is exit 3 `not_found` with `field: "issue"`; an issue
  with no edges exits **0** with empty `stdout` and `0 relations` on `stderr` (§2.4.1).
- The `READS AS` column is `RelationType.name_as_seen` of SPEC-020 §2.1 and nothing else: `blocks` when
  `REF` is `issue_id`, `blocked_by` when `REF` is `related_issue_id`, and the type's own value for the
  three symmetric types, whose pair is stored in ULID order and has no semantic direction (D-045). On
  this human surface the name is rendered with `_` as a space (`blocked by`), the rule SPEC-020 §2.1
  already states; `--quiet` prints the far end's `identifier`, one per line (R12), so a script reads the
  same set without the column. Rows are ordered by that name in the order of the §2.1 table — `blocks`,
  `blocked_by`, `duplicate`, `related`, `similar` — and then by `IDENTIFIER` ASC, so two runs over the
  same data print the same table (REQ-N050-05). The `type` and the far end are the only two facts of a
  row, and neither is recomputed here.
- `relations --json` emits `{items: Relation[]}` — the base envelope of §2.4.3 and the five keys of
  §2.4.2, `id, issue_id, related_issue_id, type, created_at`, in that order, in the sequence above. No
  key is added: there is no `direction`, no `blocked_by`, no `identifier`, no `title` and no `resolved`.
  The direction is **derived, not transported**, because a sixth key would be a second truth about one
  edge (D-046): `out` iff the item's `issue_id` is `REF`'s ULID, `in` iff it is `related_issue_id`, and
  meaningless for the symmetric types. That is enough for every consumer of the envelope: the two ULIDs
  name both ends, `REF`'s own ULID is the `id` of `issue show REF --json` (§2.4.2) or the ULID the
  caller typed, and the far end is the ULID that is not it. `resolved` is not a property of the row
  either — it is `is_hard` plus the blocker's `state.type` on read (SPEC-020 §4.1 R7), which is what
  `blocked` below answers.
- `children` is **not** part of `relations`. A sub-issue is a `parent_id` column of `issue`, not a row
  of `issue_relation` (SPEC-010 §3), so `relations` would mix two facts in one list with no column to
  tell them apart. The hierarchy is read where it lives: `issue list --parent REF` (§2.5.3.1, direct
  children, with the visibility flags) and `issue show --with children` (§2.5.3, GAP-06). `relations`
  therefore answers with the five names of `issue_relation` — `blocks`, `blocked_by`, `duplicate`,
  `related`, `similar` — and never with a sixth.
- `show --with relations` stays **GAP-06** (§2.3.1) and does not merge into `show --json`: the relations
  read is this verb, declared in v1 with its own exit set, and the day GAP-06 lands the `--with` variant
  emits the same five-key objects from the same read model (§2.4.2) — one shape, one source, no branch.
- `blocked` lists the issues that are waiting on someone else. It is one call — `list_blocked(db,
  team=KEY)` (SPEC-040 §2.2) over `blocked_view` (SPEC-030 §2.6, SQL-10) — and the predicate is
  SPEC-020 §4.1 R7, not a second definition here: an issue is listed when it is the target of at least
  one `blocks` row whose source's `state.type` is neither `completed` nor `canceled`, the derived verdict
  of D-046 (`is_hard` + `WorkflowStateType.is_terminal`, computed on read, never a stored flag). A
  blocker that is `Done` or `Canceled` releases the issue, so the verb answers "what is stuck now" and
  not "what was ever blocked".
- `blocked` prints the columns of `issue list` (§2.4.1) and emits the items `issue list --json` emits,
  ordered by `identifier` ASC: it declares no `--sort`, no `--limit` and no `--cursor`, so it paginates
  nothing and counts nothing — the cursor keys exist only where a command paginates and in v1 that is
  `issue list` alone (§2.4.3), and no total is counted (REQ-N008). `--team` narrows the read to one team and defaults to the
  team of §2.2.2 — a workspace with two teams and no `[cli].default_team` exits 2 `missing_context`
  (R4) — and a key that resolves to no team is exit 3 `not_found`. Only the two layers hide a row
  (`blocked_view` filters on `visible`, SPEC-010 §3.3), never the blocked issue's own state: an issue
  closed while a blocker is still open is exactly the row a reader has to see. An empty result exits
  **0** with `0 issues` on `stderr`, like any empty listing.

#### 2.5.3.1 `issue list` — filters, order and paging

The row of §2.5.3 is the **closed** set of flags (R17). This subsection says what each one means and
which field of `ListFilters` (SPEC-030 §2.6) it fills; the edge resolves the reference, builds that one
object and calls `list_issues`, and adds no filter of its own.

| Flag | `ListFilters` field | Note |
|---|---|---|
| `--team` | `team_id` | global (§2.2.2); ULID or key (SPEC-040 §5.3 step 2); unknown ⇒ exit 3 |
| `-s/--state` (rep.) | `state_id` / `state_ids` | name (case-insensitive, resolved team) or ULID |
| `--state-type` (rep.) | `state_type` / `state_types` | the six values of the enum |
| `-p/--priority` (rep.) | `priority` / `priorities` | `0`-`4`; `0` is `No priority` |
| `-a/--assignee` | `assignee_id` | §2.2.3 vocabulary |
| `--mine` | `assignee_id` | the resolved member (§2.2.3) |
| `--unassigned` | `unassigned=True` | |
| `-l/--label` (rep.) | `label_ids` | name (case-insensitive, resolved in the command's team and then in the workspace, §2.5) or ULID |
| `--project` | `project_id` | see the reference note below |
| `--cycle` | `cycle_id` | see the reference note below |
| `--no-cycle` | `no_cycle=True` | with `--cycle` ⇒ exit 2 `invalid_option` |
| `--parent` | `parent_id` | direct children only |
| `--query` | `q` | title filter (D-025), not search |
| `--open` (default) / `--all` | `is_open=True` / `is_open=None` | |
| `--archived` | `archived_only=True` | |
| `--trashed` | `trashed_only=True` | implies `--all`; opens the archive axis (SPEC-030 §2.6), so no second field is set |
| `--sort` | `order` | default `manual` |
| `--reverse` | `reverse=True` | |
| `--limit` | `limit` | default 50, range 1-200 |
| `--cursor` | `cursor` | opaque, from a previous `next_cursor` |

**Repeated flags are not symmetric.** Two rules, and the difference is deliberate:

- `-s/--state`, `--state-type` and `-p/--priority` are **OR inside the family**:
  `--state Todo --state "In Progress"` is "in Todo **or** In Progress" and `--priority 1 --priority 2`
  is "urgent or high". An issue has one state and one priority, so AND inside those families would
  return nothing by construction.
- `-l/--label` is **AND inside the family**: every named label must be present on the issue. This is
  what the acceptance suite asserts and what SPEC-030 §2.6 encodes with `= :label_count`.
- **Across families the combination is always AND**: `--state-type started --label bug --mine` means
  all three. A repeated value is one element (a duplicate `--label bug --label bug` is one label).
- The CLI **fills the tuple**; it does not fold two families into one or turn an OR into an AND. The
  semantics live in SPEC-030 §2.6, so the CLI, the API and the dashboard cannot drift.

**Visibility matrix.** `--open/--all` (state axis) and `--archived`/`--trashed` (layer axis) are
independent, and the cells below are the whole contract:

| Flags | `archived_at` | `trashed` | `is_open` | Returns |
|---|---|---|---|---|
| none / `--open` | `IS NULL` | `0` | `= 1` | open, live issues — the default |
| `--all` | `IS NULL` | `0` | any | open and closed, live |
| `--open --archived` | `IS NOT NULL` | `0` | `= 1` | archived issues that were still open |
| `--all --archived` | `IS NOT NULL` | `0` | any | every archived issue |
| `--trashed`, `--all --trashed` | any | `= 1` | any | the trash, archived or not |
| `--archived --trashed` | — | — | — | exit 2 `invalid_option` |

Three consequences worth stating because they are the questions the flags raise: `--archived` **never**
looks inside the trash (a trashed issue is reachable with `--trashed` alone); `--trashed` **ignores**
`archived_at`, because trash is the deeper layer and an issue that was archived and then trashed would
otherwise be invisible from every listing — the archive predicate of SQL-4 carries that exception
(SPEC-030 §2.6), so this table has exactly one field per flag; and `--all --trashed` is exactly
`--trashed` — the flag already implies `--all` — so the pair is not an error.

**`--query` is a title filter, not search.** It fills `ListFilters.q`: `LIKE '%term%'` over `title`,
case-insensitive, with the term's `%`, `_` and `\` escaped (D-025). A whitespace-only value is dropped
and is not an error. It does **not** touch FTS5, descriptions, comments, identifiers or the
`field:value` grammar: that is `hifa search` (SPEC-090), which is a different verb with a different
envelope. Combining `--query` with any other flag ANDs it, like every other family.

**`--parent` lists direct children, not a subtree.** The predicate is `parent_id = REF`, so
grandchildren are excluded — a child's children carry the child's id as their parent. REF resolves like
any other reference (identifier or ULID of the resolved team) and an unknown one is exit 3
(`field: "parent"`). The children are then filtered by the same visibility flags as everything else:
`--parent ENG-1` with the default `--open` lists the open children only.

**References resolve inside the resolved team; a value that matches nothing is an error here.** Every
one of `--state`, `--label`, `--assignee` and `--parent` resolves through the repositories of
SPEC-030, and a value with no match is exit 3 `not_found` whose `field` names **the resource the flag
resolves** — the noun the use case's `NotFound(resource=...)` carries, `member` for `-a/--assignee`
(§2.2.3, SPEC-040 §5.4) — and never the flag's own spelling. The dashboard's
drop-the-filter rule for a stale bookmark (SPEC-030 `resolve_filters`, D-027) is a property of the web,
not of this edge: a typo in the CLI is never a silently unfiltered listing. `--project` and `--cycle`
are the two exceptions in v1: their reads do not exist yet (GAP-03), so the value is passed through as
`project_id`/`cycle_id`, which means it must already be the ULID the filter compares; a name there is
out of contract until those reads land.

**Order.** The five orders, their `sort_key` and their direction are SPEC-030 §2.6.1 and are not
re-decided here: `manual` (default) is `sort_order` ASC; `created` and `updated` are ASC; `priority` is
ASC with `No priority` (0) last; `due` is ASC with the undated last. `--reverse` inverts the key **and**
the `id` tie-breaker together — the values — and never the position of the rows without a value:
`No priority` and the undated issues are last in **both** directions (D-044), so `--reverse --sort due`
prints the latest due dates first and the undated at the end, and the same holds for `No priority`
under `--reverse --sort priority`. Two runs over the same data print the same order — `REQ-N050-05`
makes the JSON byte-identical.

**Paging.**

- `--limit` is 1-200, default 50. Out of range is exit 2 `validation_error` with `field: "limit"`
  (`LIMIT_RANGE`, raised by `list_issues` and not by the parser).
- `--cursor` is opaque and comes from the `next_cursor` of the previous page. The CLI never builds one
  and never accepts `--offset` (R7).
- `next_cursor` is non-null **iff** `has_more` is true. `has_more: true` implies the page carries
  exactly `--limit` items, because the adapter asked for one more and trimmed it.
- The last page has `has_more: false` and `next_cursor: null`, even when it is exactly `--limit` long.
- An empty page is exit 0 with `{"items": [], "next_cursor": null, "has_more": false,
  "total_estimate": null}`, an empty `stdout` in table mode and `0 issues` on `stderr` (§2.4.1). A
  cursor that lands past the end of the result set is that empty page, not an error.
- A cursor that is unreadable or truncated, that comes from another `--sort` or another direction, or
  whose anchor does not exist in the team is exit 2 `validation_error` with `field: "cursor"`
  (`INVALID_CURSOR`). It is never a silent restart at page 1.
- `--limit` may change between pages: the page size is not part of the cursor.
- The cursor is **positional, not a snapshot**: an issue created or closed between two pages shifts
  what the next page contains, but not whether the cursor is valid. For the data as it is read, the
  `id` tie-breaker is what guarantees no duplicates and no holes at the page boundary.
- `--quiet` still prints one identifier per line, one per item (R12); paging changes nothing about the
  format.

`cycle create`: `ends_at` > `starts_at` (schema CHECK) and `number` = `MAX(number)+1` of the team.
`starts_at`/`ends_at` are persisted as `YYYY-MM-DD` (calendar date, D3). `cycle close`
writes `completed_at` = now; closing an already closed cycle exits **4** `CYCLE_ALREADY_COMPLETED`
(SPEC-040 §2.2 — the repeat is the conflict, not a workflow rule). `complete_cycle` has no
clock-based refusal: a cycle whose `ends_at` is still in the future is closed like any other, so
`cycle close` never exits 5 and v1 has no `--force` (D-042).
`member deactivate` fails with `Conflict` (exit 4) if the member is `lead_id` of any non-archived project
or `assignee_id` of open issues: reassignment must come first.

**The five label verbs are one family, and the scope of a name is the one §2.5's conventions declare.**
`REF` is a ULID or a name; for `show`, `update` and `archive` a name resolves case-insensitively over
the whole workspace — **retired rows included**, which is what lets `label archive NAME --undo` reach a
retired label and `label update NAME --name NEW` rename one — and a name that matches labels of two
teams is exit 2 `validation_error` with `field: "ref"` (`LABEL_AMBIGUOUS`, SPEC-040 R22) instead of a
silent pick: those three take no `--team` to narrow it, and a guess is worse than a refusal. `--parent`
is **not** resolved that way: it is a group of the new label's own level — a group of `--team`'s team
for a team label, a workspace group when the label is a workspace one — and a parent that exists only
elsewhere is exit 2 (`LABEL_GROUP_INVALID`, `field: "parent"`). `hifa label list --json --all` is how a
caller reads the ULID of a retired label; without `--all` the listing hides those rows, because a
listing renders a catalogue and a `REF` acts on one labelled row (SPEC-040 §2.2).
`--team` on `add` names the team the label is created in, and on `list` the team whose catalogue is
printed; neither scopes a `REF`.

- **`list`** prints `NAME COLOR TEAM RETIRED`, ordered by `name` ASC and then by `id` ASC (REQ-N050-05:
  two runs over the same data print the same table). `TEAM` is the row's `team_id` **as stored** — the
  ULID the canonical `Label` of §2.4.2 carries, because no use case of SPEC-040 returns a team key and
  the edge issues no read of its own to translate it — or `–` for a workspace label; `RETIRED` is `–` or
  the instant in the format of §2.7's `CREATED` (`2026-11-20T14:22:05Z`).
  With no `--team` it lists **every** label of the workspace, both levels; with `--team KEY` it lists the
  labels an issue of that team can wear — that team's **plus** the workspace ones (SPEC-040 §2.2), which
  is the set `issue label` accepts. `--all` adds the retired ones; without it every row with
  `retired_at` set is hidden. `--json` is `{items: Label[]}` in the same order, each item the canonical
  `Label` of §2.4.2 (nine keys, `retired_at` included, `team_id` a ULID).
- **`show`** prints the key-value block of §2.4.1: `NAME`, then `Color`, `Team` (the same `team_id` ULID
  as `list`'s `TEAM` cell, or `–`), `Group` (`multiSelect`, `singleSelect` or `–`), `Parent` (the
  group's name or `–`), `Description` (`–` when
  NULL) and `Retired` (`–` or the instant). `--json` is the canonical `Label` and nothing else: the read
  is `label_detail`, the four foreign values are its own columns.
- **`add`** is the only path to a group, to a workspace label and to a description (SPEC-040 R22).
  `--group` creates a group and needs no `--parent`; `--parent` creates a child of that group;
  `--group` together with `--parent` is exit 2 (`LABEL_GROUP_INVALID`, `field: "parent"`), because a
  group has no parent in the schema. `--team` and `--no-team` together are exit 2 `invalid_option`;
  neither is a workspace label, which is what REQ-F024 already says. A repeated name at the same level
  is exit 4 `conflict` (`UNIQUE_LABEL_NAME`), a color outside `#RRGGBB` exit 2 (`COLOR_FORMAT`), a
  blank `--name` exit 2 (`LABEL_NAME_EMPTY`), and a `--parent` that is not a group of the same level
  exit 2 (`LABEL_GROUP_INVALID`, `field: "parent"`).
- **`update`** renames, recolors and re-describes: `--name`, `--color`, `-d/--description` and
  `--clear-description` (which sends `None`; an `-d ""` is normalized to `None` too). It changes no
  `team_id`, no `parent_id`, no `is_group`/`group_type` and no `retired_at` — the level of a label is
  not editable in v1 (SPEC-040 R22). **`--clear-description` together with `-d/--description` is exit 2
  `invalid_option`** (`field: "description"`), not a precedence: the pair says "clear it" and "set it to
  this" about one column, and a flag that contradicts another flag is a bad invocation, the same answer
  `--json` with `--quiet` and `--team` with `--no-team` already get (§6). With **no flag at all** it
  exits 2 `no_changes`, before opening the database, like `issue edit`; with flags whose values equal
  the stored ones it exits **0**, writes nothing and returns the label. A rename to a name already taken
  at the same level is exit 4 (`UNIQUE_LABEL_NAME`). A retired label may be renamed: the row is its
  record and the fix is worth having. `issue_label` is untouched — every chip follows the rename,
  because the link is by ULID.
- **`archive`** sets `retired_at` (`retire_label`) and `--undo` clears it (`restore_label`), which is
  the one way back: there is no `label delete` and no physical delete (D-015). Retiring a label **in
  use** is exit 4 `conflict` (`LABEL_IN_USE`): in use means at least one `issue_label` row, whatever
  layer the issue is in (SPEC-040 R22, D-061), so detach the label from every issue first. Retiring an
  already retired label is exit 4 (`LABEL_RETIRED`); `--undo` of a label that is not retired is exit 4
  (`LABEL_NOT_RETIRED`), the same shape and the same code family, not a silent no-op. The exit set is
  `0,2,3,4`: `2` is the shared `LABEL_AMBIGUOUS` of the family and nothing else, because this verb has
  no flag combination to refuse. There is no `--yes`: a retire deletes nothing and is undone by one
  command, so a prompt would only stand between the reader and a reversible write.

the data goes to `stdout` and the report to `stderr`. Data format: SPEC-080.

as `hifa export --format … --out …` (SPEC-080 §2.3). The `4` of `import` can only come from
`destination_exists` (`--mode replace` without `--force`); row errors are exit 2 and there is no
global rollback in v1 (SPEC-080 §6.1). The tree of §2.5 declares **a single** `doctor`: `hifa doctor`
(SPEC-100 §2.7), also the only source of its `--json` envelope. There is no second diagnostic
command under `db`, nor an alias with its own handler.

#### 2.5.6 `state`

| Command | Arguments / flags | `--json` | Exit |
|---|---|---|---|
| `hifa state list` | `--team KEY` (default: the team resolved by 2.2.2) | `{items: State[]}`, each item + `issues_count` | 0,2,3 |
| `hifa state create NAME` | `NAME` positional (required); `--type {triage,backlog,unstarted,started,completed,canceled}` (required), `--color HEX` (default `#6B6F76`), `--team KEY`, `--before NAME`, `--after NAME` | `State` | 0,2,3,4 |
| `hifa state update NAME` | `NAME` positional (required, case-insensitive); `--name NEW`, `--color HEX`, `--before NAME`, `--after NAME`, `--team KEY` | `State` | 0,2,3,4 |

The sub-app is registered in §2.1 and has **three** handlers, one per verb. It is numbered §2.5.6
and not §2.5.3 because §2.5.3–§2.5.5 are cited by section from SPEC-010, SPEC-060 and D-031; the
tree of §2.5 is ordered by family, not by menu order.

- This section publishes the surface of `create_state` / `update_state` / `list_states`
  (SPEC-040 §2.2). The CLI **validates nothing and touches no SQL**: it resolves names, builds the
  command object of §2.1, calls the use case and formats the result.
- **`list`** orders by `position` **ASC** — `workflow_state.position`, not name, not `created_at` —
  and prints `POSITION NAME TYPE COLOR DEFAULT ISSUES`. `POSITION` is rendered with **as many
  decimals as the stored value needs**, trailing zeros trimmed and at least one (`1.0`, `2.0`,
  `2.5`, `4.75`, `4.9375`), so two distinct positions never print the same number; `--json` stays
  exact either way, because the column renders the value and never substitutes for it. A fixed one
  decimal (`f"{value:.1f}"`) rounded two positions into one: three `--before Done` inserts in this
  tree store `4.75 / 4.875 / 4.9375` and printed `4.8 / 4.9 / 4.9`, and three `--after 'In
  Progress'` inserts store `4.0625 / 4.125 / 4.25` and printed `4.1 / 4.1 / 4.2` — in both cases
  the reader is shown one number where the database holds two positions, and the order of the
  board stops being readable from the table. `DEFAULT` is `*` for the row with `is_default = 1` and
  `–` otherwise; `ISSUES` is the number of issues whose `state_id` is that state and that are visible
  (`archived_at IS NULL AND trashed = 0`), i.e. the same population as `v_team_progress`
  (SPEC-010 §3.3). A state with no issues prints `0`, never a blank. `--json` emits
  `{items: State[]}` in that same order, each item carrying `issues_count` as an **additive**
  field (default `0`, D-026); `State` is the canonical object of §2.4.2
  (`id, name, type, color, position, is_default`).
- **`NAME` is case-insensitive** within the resolved team (2.5 conventions, `refs.py`): `todo`,
  `Todo` and `TODO` name the same state. An unknown `NAME` (or `KEY`) ⇒ exit 3,
  `not_found`, and the message names the state the user typed.
- **Error codes come from SPEC-040 §6, not from here.** `--type` outside the six types ⇒ exit 2,
  `validation_error` with `error.field: "state_type"` (`Validation(STATE_TYPE_INVALID)`); a blank
  `NAME` ⇒ exit 2 (`Validation(STATE_NAME_EMPTY)`); a `--color` outside `^#[0-9A-Fa-f]{6}$` ⇒ exit 2
  (`Validation(COLOR_FORMAT)`); a name that already exists in the team, and a `--name NEW` that
  collides with a sibling, ⇒ exit 4, `conflict` (`Conflict(UNIQUE_STATE_NAME)`) — that is the
  duplicate code of §2.6 for states, and the CLI invents no other.
- **`--before NAME` / `--after NAME` are the human form of the reorder.** The user never types a
  float and never sees `position` in a flag: the CLI resolves the anchor (same team, same
  case-insensitive rule; an anchor that does not exist ⇒ exit 3), reads the team's states with
  `list_states`, computes the target `position` with `domain.ranking.between(prev, next)` — the
  same helper `move_issue` uses (SPEC-040 R8, R9) — and sends it in the command:
  `CreateState(position=…)` or `UpdateState(position=…)`. `--before A` means "immediately to the
  left of A" (`between(position_of_previous_state, position_of_A)`); `--after A` means
  "immediately to the right of A". With neither flag, `create` appends **after the last state**
  (`CreateState.position = None`, which SPEC-040 already defines as "last of the team") and
  `update` leaves `position` at `UNSET`. `--before` and `--after` together ⇒ exit 2
  `invalid_option`. Gap exhaustion on `workflow_state.position` is **not** rebalanced in v1
  (`rebalance_board` only touches `issue.board_order`): `RANKING_EXHAUSTED` ⇒ exit 2,
  `validation_error`, and the message names the two neighbors.
- **No other verb.** `hifa state` publishes `list`, `create` and `update` and nothing else: there is
  no `state archive`, no `state delete`, no `--archived`, no `--force` (D-035). Archiving or
  deleting a state needs a decision about the issues that live in it, and that decision is not
  taken; the surface does not promise it. `state update` therefore cannot empty a state either —
  moving issues is `hifa issue move` (SPEC-040 §2.2, `move_issue`).
- The **canonical order of a new team** is `DEFAULT_STATES` (SPEC-100 §2.5): `Triage`, `Todo`,
  `Backlog`, `In Progress`, `In Review`, `Done`, `Canceled` at `1.0, 2.0, 3.0, 4.0, 4.5, 5.0, 6.0`
  (D-034 for the order of the six that predate it, D-058 for `In Review`). A team initialized before
  D-034 keeps `Backlog` at `2.0` until its owner runs `hifa state update Backlog --after Todo`, and a
  team initialized before D-058 gets the review column with `hifa state create 'In Review' --type
  started --color '#BB87FC' --before Done`; the route for both is this command or the drag on the
  board (SPEC-070 §2.6.5), and **no migration renumbers `workflow_state`**.

### 2.6 Exit codes (normative)

Single map, identical to **D-014** (`specs/DECISIONS.md`). `doctor` is the **only** exception and
extends the map with `0/1/2/3` per SPEC-100 §6 (D-001).

| Code | Name | Cause | `error.code` |
|---|---|---|---|
| 0 | ok | success, including idempotent no-op | — |
| 1 | warn | **exclusive to `hifa doctor`**: there is a `warning` and no `critical` | — |
| 2 | validation | invalid input, incompatible flags, unresolvable context, invalid config | `validation_error`, `invalid_option`, `missing_context`, `invalid_config`, `no_changes`, `confirmation_required` |
| 3 | not found | nonexistent entity, database, file or label | `not_found`, `database_not_found` |
| 4 | conflict | uniqueness, references in use, duplicate, newer schema | `conflict` |
| 5 | invalid transition | a write on an archived issue (2.6.1) | `invalid_transition` |
| 6 | internal | unmapped exception, corrupt database, missing `[web]` extra | `internal_error`, `missing_web_extra`, `corrupt_database` |
| 130 | interrupted | `SIGINT` (Ctrl-C), POSIX convention, outside the domain mapping | `interrupted` |

No other command uses `1`: an internal bug is `6`. `hifa doctor` does not use `4/5/6` (SPEC-100 §6).

#### 2.6.1 Conditions of `invalid_transition` (exit 5)

There is exactly one in v1:

1. the issue has `archived_at IS NOT NULL` and the command writes it, or writes a row that hangs off
   it — `ISSUE_ARCHIVED`, the single producer of R20 (SPEC-040 §6, D-042): an archived issue is not the
   source of a transition nor of a field write, `restore` is the only write that accepts one, and
   `comment_on_issue` is refused the same way although the row it would write is a `comment`. The
   message names the issue and the payload carries `field: ref` (§6).

Every other state-machine rejection is `Validation` (exit 2), because SPEC-020 §2.5 raises it:
`CLOSE_WITH_OPEN_CHILDREN` (a terminal target or an archive with open sub-issues), `STATE_ARCHIVED`
(target `workflow_state` with `archived_at` not null), `STATE_TEAM_MISMATCH` (target state of another
team, which breaks the composite FK of SPEC-010 R4) and `ISSUE_TRASHED`. Exit 5 comes from the
application layer (SPEC-040 §6) and from nothing else: `cycle close` has no clock-based refusal
(§2.5.4), so no command of this edge produces it for a second reason.

## 3. Data it touches

The CLI **writes no SQL and opens no connections**: it operates on entities through the use cases
of §2.3, which in turn use the `UnitOfWork` of SPEC-030. This table declares the observable effect
per command; the invariants are those of the SPEC-010 schema and are not re-validated here.

| Entity / table | Operation | Commands | Invariant backed by the schema |
|---|---|---|---|
| `workspace` | INSERT | `init` | 1 row per database; `url_key` UNIQUE |
| `team` | INSERT / UPDATE `archived_at` | `team create` (archiving is deferred, D-031) | `UNIQUE(workspace_id, key)` |
| `workflow_state` | INSERT (init) | `init` | `UNIQUE(team_id, name)` |
| `issue` | INSERT / UPDATE | `issue create\|edit\|move\|assign\|archive\|delete\|restore` | `UNIQUE(team_id, number)`, `UNIQUE(identifier)`, `CHECK(priority 0..4)` |
| `issue_label` | INSERT / DELETE | `issue create`, `issue label\|unlabel` | PK `(issue_id, label_id)` ⇒ idempotent operation, and at most one label of a `singleSelect` group per issue (SPEC-040 R10) |
| `issue_relation` | INSERT / DELETE | `issue relate [--undo]` | `UNIQUE(issue_id, related_issue_id, type)`, `CHECK(issue_id <> related_issue_id)` |
| `comment` | INSERT / SELECT | `issue comment` | `CHECK(length(trim(body)) > 0)` |
| `attachment` | INSERT / SELECT | `issue attach` | `url` NOT NULL; `metadata` is serialized JSON |
| `issue_history` | INSERT (implicit, by the use case) | every `issue` mutation | one row per changed field |
| `project` / `project_milestone` | INSERT / UPDATE | `project *` | `priority BETWEEN 0 AND 4` |
| `cycle` | INSERT / UPDATE `completed_at` | `cycle *` | `UNIQUE(team_id, number)`, `CHECK(ends_at > starts_at)` |
| `member` / `team_membership` | INSERT / UPDATE `is_active` | `member *` | `email` UNIQUE |
| `label` | INSERT / UPDATE (`name`, `color`, `description`, `retired_at`) | `label add\|update\|archive\|archive --undo`, `issue label --create` | `UNIQUE(workspace_id, team_id, name)` through the two partial indexes of D-010 |
| `v_issue`, `v_priority`, `v_team_progress` | SELECT | `issue list\|show`, `team show`, `search` | read-only views (SPEC-010 §3.3) |
| `issue_fts` | SELECT | `search` | index maintained by triggers (SPEC-090) |

Nothing is ever written directly to `v_*` or to `issue_fts`.

## 4. Business rules

Every rule is verifiable by a test. The `REQ-*` are the auditable form of the same rule.

| ID | Rule |
|---|---|
| **R1** | **A6 — a single formatter.** No module under `cli/commands/` calls `print`, `typer.echo`, `sys.stdout.write` or builds ANSI. Everything goes through `cli/output.py`; a static test forbids those calls outside `output.py` and `errors.py`. → **REQ-F050-01** |
| **R2** | **One JSON shape per entity.** `--json` always emits the complete object of §2.4.2, with all its keys and in that order; no command adds or removes keys (the `--with` variants append at the end, never reorder). ## 5. Flow

### 5.1 Read command (`issue list`)

```
1. Typer parses argv and calls the root callback.
2. main callback: --json/--quiet/--no-color → ctx.format, ctx.color; --db/--team/--member → overrides.
3. context.resolve(): resolve_config (SPEC-100) → absolute db path → team → member.
4. Open the UoW (read-only when the command does not mutate). A failure is database_not_found → exit 3.
5. Build ListFilters (SPEC-030 §2.6) from the flags; validate the combinations (--archived+--trashed, …).
6. Call app.list_issues(db, filters) and keep the keyset page (D-011).
7. output.render(ctx, items, cursor): table | json | quiet.
8. Close the UoW. exit 0.
```

### 5.2 Mutation command (`issue move`)

```
1..4 as in 5.1 (the UoW in write mode: BEGIN IMMEDIATE inside the use case).
5. Resolve REF → issue (exact identifier first, then ULID). Not found → exit 3.
6. Resolve --state to a workflow_state of the issue's team (case-insensitive name, then ULID).
   No match → exit 3 field "state"; ambiguous match → exit 2.
7. app.move_issue(uow, MoveIssue(issue=REF, target_state=…, position=…, before_id=…, after_id=…), actor):
   validates 2.6.1 (it may raise InvalidTransition), computes board_order with ranking.between
   (SPEC-040 R8) and rebalances when it must (R9), writes issue.updated_at, inserts
   issue_history(field="state_id").
8. COMMIT. Any exception → ROLLBACK and the mapping of cli/errors.py.
9. output.render(ctx, issue) → exit 0.
```

### 5.3 Exception-to-exit-code mapping

```
try:
    result = use_case(...)
except Validation as e:      exit 2  (code=validation_error, field=e.field)
except NotFound as e:        exit 3  (code=not_found, field=e.field)
except Conflict as e:        exit 4  (code=conflict, field=e.field)
except InvalidTransition as e: exit 5 (code=invalid_transition, field=e.field)
except KeyboardInterrupt:    exit 130
except Exception as e:       exit 6  (code=internal_error; traza completa solo si HIFA_DEBUG=1)
```

The handler lives in `cli/errors.py` as a global `app = typer.Typer(...)` plus an
`@app.callback` that wraps the invocation; no command does `try/except` on domain errors.

## 6. Errors

| Domain error | When | Message (`stderr`, without `--json`) | `error.code` | Exit | HTTP (SPEC-060) |
|---|---|---|---|---|---|
| `Validation` | invalid flag, illegal combination, malformed date, state from another team | `hifa: <detail> (field: <field>)` | `validation_error` | 2 | 422 |
| `InvalidOption` | `--json` with `--quiet`, `--after` with `--before`, `--mine` with `--assignee`/`--unassigned`, `--unassigned` with `--assignee`, `--archived` with `--trashed`, `--cycle` with `--no-cycle`, `--color` without `--create` on `issue label`, `--team` with `--no-team` on `label add`, `-d/--description` with `--clear-description` on `label update` | `hifa: --json and --quiet are mutually exclusive (field: output)` | `invalid_option` | 2 | 422 |
| `MissingContext` | unresolvable team/member | `hifa: team required: use --team, HIFA_TEAM or [cli].default_team in .hifa.toml` | `missing_context` | 2 | — |
| `InvalidConfig` | `.hifa.toml` with a wrong type or broken TOML | `hifa: invalid .hifa.toml: <detail> (field: <key>)` | `invalid_config` | 2 | — |
| `NoChanges` | `issue edit` with no flags, `label update` with no flag | `hifa: nothing to change` | `no_changes` | 2 | — |
| `ConfirmationRequired` | destructive operation without `--yes` | `hifa: operation canceled` | `confirmation_required` | 2 | — |
| `NotFound` | nonexistent REF/team/member/label/project/cycle/link | `hifa: issue 'ENG-999' does not exist (field: issue)` | `not_found` | 3 | 404 |
| `DatabaseNotFound` | missing SQLite file | `hifa: database not found at <path>; run 'hifa init'` | `database_not_found` | 3 | 503 |
| `Conflict` | uniqueness, label in use, member with open issues, team with issues | `hifa: team with key 'ENG' already exists (field: key)` | `conflict` | 4 | 409 |
| `InvalidTransition` | 2.6.1 (1) | `hifa: ENG-13 is archived; restore it first (field: ref)` | `invalid_transition` | 5 | 409 |
| `MissingWebExtra` | `serve` without `[web]` | `hifa: missing the web extra; install 'hifa[web]'` | `missing_web_extra` | 6 | — |
| `CorruptDatabase` | `integrity_check` fails | `hifa: corrupt database: <detail>; see 'hifa doctor'` | `corrupt_database` | 6 | 500 |
| unmapped `Exception` | bug | `hifa: internal error: <type>: <msg>` | `internal_error` | 6 | 500 |
| `KeyboardInterrupt` | Ctrl-C | (nothing) | `interrupted` | 130 | — |

Message catalog (the exact text is part of the contract because the tests assert it):
messages carry **no** trailing period, start in lowercase, quote the identifier with single
quotes, and append `(field: <field>)` only when there is a field.

`issue comment` prints three of them of its own, and the dashboard prints the same three (§6 of
SPEC-070), so neither edge invents a wording: `a comment needs a body (field: body)`, `the thread is 3
deep; reply to a shallower comment (field: parent_id)`, and `that comment belongs to another issue
(field: parent_id)`.

The two layers are two different exits, and a comment does not merge them. A **trashed** issue is
`Validation` (exit 2) and the message names it: `ENG-30 is in the trash; restore it first`. An
**archived** one is the `InvalidTransition` row above (exit 5), whose message names the issue the same
way: `ENG-13 is archived; restore it first`.

## 9. Provenance

- Command and flag vocabulary: pattern from `gh`, `jj`, `bd` and `linear-cli`; the
  `resource verb` form (`hifa issue move`) follows the `git`/`gh` convention and avoids ambiguous
  positional flags.
- `identifier` as the primary argument (instead of ULID): author's decision, 2026-11-08 —
  the ULID is a storage detail, the identifier is what the human types.
- Exit codes 0/2/3/4/5/6: aligned with the domain error table of SPEC-000 A7 and with the
  `grep`/`diff` convention (2 = usage error), not with `sysexits.h`.
- `--json` with `indent=2` and the base envelope `{items}` (plus `next_cursor`/`has_more`/
  `total_estimate` only where the command paginates, D-031): the collection is always an object, never
  a bare array, so a script can swap CLI for HTTP without changing its parser.
- `total_estimate: null` instead of `total`: `COUNT(*)` over 10 000 rows violates REQ-N008; measured
  in the prototype (18 ms for `COUNT` vs 4 ms for the keyset page).
- `hifa label add|list|archive` was added (it was not in the original 050 brief): `issue label`
  requires existing labels and SPEC-060 exposes `/labels`; without it the command is not usable.
  `label show`, `label update` and `--undo` joined it with D-061, for the same reason from the other
  side: a catalogue nobody can rename, inspect or un-retire from is a table only SQLite can maintain.
- `rich` prohibition: a 4-column table does not justify 12 ms of import or 8 MB of RSS,
  measured against the REQ-N050-02 budget.

## 10. Out of scope

- Installed shell completion (Typer generates it; its content is not tested).
- Interactive/TUI mode, embedded editor (`$EDITOR`), multi-step prompts.
- `hifa watch`, `hifa tui`, `hifa sync`.
- Message translation: the strings of §6 are in English and are not internationalized.
- Data format for import/export (SPEC-080) and search ranking (SPEC-090).
- Multi-workspace administration commands (`hifa workspace *`).
